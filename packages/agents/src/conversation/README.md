# Shared conversation pipeline

`createConversationPipeline` uses only the public runtime/model/tool ports. Persistent mechanics live in core step snapshots, Run `state`, and `sessionState`; this module queries no teaching tables. Tool port signatures remain compatible.

`limits` fixes a Run basis on its first prepared step: 16 model operations (including summaries/policy), 64 dispatched tool commands, 1,048,576 input tokens, 65,536 output tokens, 600,000 ms per call and a 24-hour deadline. Completed final provider counters settle reservations; missing/partial counters retain the configured context/output reservation. Estimates only trigger compaction and are never exact usage. CPU yields, retries and process recovery do not reset this basis.

Native tools settle before any prefix/model transition. Transitions retain the original target, source/pin, request identity and authorized visible history. Only portable text crosses a route; native signatures/reasoning stay at their model owner. `scenario.authorizeHistory` may reauthorize/filter history before preparation; transfer and summary adoption recheck that fixed history. Unresolved original native work pauses rather than inventing a pairing or a new effect.

`compaction` optionally configures `{ policy, provider }`; `false` disables it. The default provider is independent of core/domain storage. Selection fixes source versions, digests, required context/effects and one summary attempt. The summary and its adoption record commit with the core result/session state. Unknown and interrupted results reconcile at the original owner. A stopped Run's pending compaction is not dispatched under a new Run identity.

All returned waits are retained in `state.waitQueue` and the `tool-waits` event, including external accepted work. Core currently admits one wait per settlement: the pipeline activates this queue serially using `conversation.wait` operations. Original single-wait presentation remains unchanged. Human questions block subsequent effects even if question preparation failed. Only the owning module validates user answers; host `resolveWait` supplies trusted external completions. External completion does not override core's explicit restart/continue policy. An accepted tool may explicitly return `continuation: true`: the pipeline settles its native pair while retaining `keepDispatch` on the original command and binds the external wait with `continuationOperationId`. Core resolves/revokes that original permit; no replacement command or bypass of generation checks is introduced. Transport outcome codecs must accept the optional boolean.

A wait may opt in with `interruptible: true`; `user-questions` sets this flag explicitly, while external effects default to retained waits. Core accepts steering and atomically cancels opted-in waits without recording an answer. The pipeline skips superseded queued questions and resumes cancelled waits only with real newer steering, forwarding their actual version, presentation and null answer as a `wait-cancelled` observation. This is also retained in portable history. Cancellation never enters response-policy classification or creates confirmation authority. Settlement/public wait schemas and dependency outcome codecs must preserve `interruptible`; core must not infer it from a business kind.

`progressPort.recordProgress(identity, originalPermit, progress)` publishes gateway-filtered progress to core only for `model.call`. Internal input-policy and compaction operations keep their original model-owner progress/results and never invoke either public progress sink. Existing `progress(snapshot, step, permit, progress)` callbacks remain supported. A prepared model call renews its actual dispatch with `{ formatVersion: 1, permit }`; reconciliation never changes the attempt or replays an unknown result.

`inputPolicy` is optional. Its fixed `input.policy.open/call` operations run before context retrieval and the primary answer, with no tools/portable history. Input bytes/version/SHA-256, policy identity, attempt and result reference bind `state.inputPolicies[inputId]`. Optional choice/text-response classification (`classifyResponses`) binds `state.responsePolicies[waitId]` to the consumed question and exact response digest. Both consume the same Run budget/permit; prepare hooks never call a model.

Student hosts use `createStudentInputPolicy` and the read-only `authorizePersonalProjectCreation(context, content)` from `@xunjie/agents/student-assistant/creation-policy`. `createStudentAssistant` installs this policy by default; workspace assembly does not. The helper checks the original completed classifier step/result, current input bytes/version, or a separately fixed semantic result for the consumed question and exact choice/text response. Choice IDs must exist in the real question; no button label grants authority. The classifier must distinguish personal project/independent learning workspace creation from creating functions, documents or files. Model tool claims grant no authority. New steering inputs supersede older input authority; unstarted commands receive not-dispatched native feedback before the new input is reviewed. `inputPolicy: false` is available for a host with an independent trusted policy.

`createStudentAssistant({ models, tools, ...options })` uses exactly the supplied readonly `ConversationToolModule[]`, including an empty array. This path does not read `learning`, `documents` or `skills`; the owning host supplies all fixed modules (including questions/material/PDF/Skills capabilities). The scene prompt, input policy, compaction and shared runtime pipeline remain identical. If `tools` is omitted, `learning` is required and the factory assembles its existing learning/user-question modules plus optional documents/Skills. Agent-only deployments can pass dependency tool modules without any learning database adapter.

Image feedback retains fixed refs/versions, image metadata and original tool provenance in session state. Each fresh conversation segment receives those actual images on its first model call, after the original module reauthorizes its source through read-only `reconcile` and the gateway freshly reads the original image owner. Source context retains one original model basis and its completed tool receipt, with no recursive Run/session history. Native tool pairs settle first; portable history transfers no provider tool-call IDs, reasoning or signatures. Compaction retains image provenance rather than substituting a textual visual claim. Image inputs are included in the whole-context input reservation and final provider usage; byte counts are recorded separately and never treated as exact tokens.

A target without image capability pauses with `image-input-unavailable`; revoked/unavailable fixed source reads pause with `image-source-unavailable`. The existing eight-image call envelope remains enforced. Paired Gateway receive must accept the original image/segment destination binding: a rejected binding pauses with `image-owner-route-unavailable`. There is no automatic upload or ownership transfer fallback. Completed/unknown attempt recovery reads the original owner result and never re-dispatches an old page tool or a replacement paid request.

A trusted tool module may return an unfinished observation with `nextCommand` to complete a partially committed operation. Reconciliation only proposes the command; a separate core step obtains a fresh dispatch permit before any write. The original module version, binding, model basis and native call ID remain fixed. Only the final outcome settles that native pair and updates the original logical tool record/card. Each continuation consumes the same Run budget; unknown observations without a continuation remain paused at their original operation.

Large tool results retain their complete committed facts. Model feedback stays valid JSON within 8192 UTF-8 bytes and supplies the fixed command/digest. `read_tool_result` is exposed only after such a projection exists; it reads bounded original byte ranges from the same authorized Run, rechecks the original module binding and never accepts storage resource IDs.
