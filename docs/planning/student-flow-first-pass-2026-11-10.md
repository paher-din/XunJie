## 2. P1：活动重开后运行一直等待

编号 **SF-01**；分类：功能缺陷；优先级 P1（主要操作中断，但刷新可恢复）。证据来自两次实际复现。

**正常路径的最小复现：**

1. 进入已能正常运行的 ALU 活动，保留一份有效作品和输入。
2. 打开“活动”菜单，选择“关闭活动”。
3. 再选择“重新开始活动”，确认“活动已关闭”标记消失。
4. 点击“运行”。
5. 页面持续显示“等待运行…”和“已接收运行，正在等待真实结果后启用”；点击“核对运行状态”仍不恢复。
6. 刷新浏览器后，等待指针消失，运行按钮恢复可用，本例恢复为 `F=0001 Cout=1`，原代码和输入保留。

另一条复现路径是直接在已关闭活动中点击仍然可用的“运行”，然后重开活动，结果同样卡住。正常重开路径也会触发，因此仅禁用关闭状态的按钮不足以修复。

预期：重开活动后能继续按原活动身份编辑和运行；提交的动作最终应得到真实结果或可处理的失败。关闭状态允许哪些操作应统一规定，不能允许提交后永久等待。依据为本轮保存恢复要求，以及现有“关闭/重新开始”操作的可见语义；关闭后是否允许某类离线编辑仍需核对契约。

[关闭状态下仍能发起运行](evidence/student-flow-2026-11-10/closed-activity-run.png) · [刷新后的恢复结果](evidence/student-flow-2026-11-10/reloaded-recovered.png)

### 当前代码与原因判断

- [LearningApp](../../apps/web/src/product/LearningApp.tsx) 的 `changeStatus` 用返回值替换整个 `activity` 对象。
- [ActivityReferences](../../apps/web/src/product/ActivityReferences.tsx) 中，`draft/workspace/actions` 按稳定活动身份缓存；`execution/sessions` 则依赖整个 `activity` 对象。
- 生命周期 effect 的清理同时销毁上述五类对象。状态变化重建 `execution/sessions` 时，仍被复用的 `draft/workspace/actions` 也已被销毁。
- [动作队列](../../apps/web/src/reliable-workspace/actions.ts) 的 `dispose()` 设置永久 `disposed` 标记，`open()` 不复位；通知和派发路径会因该标记提前返回。
- [ALU 操作区](../../apps/web/src/course-tools/alu/AluExperimentTool.tsx) 的 `canWrite/canAct` 未纳入活动关闭状态；课程对话区域则有关闭状态保护。

这是与现象吻合的高可信原因判断，尚未通过修复后的回归证明。不要将所有等待问题都归因于此，也不要把“重新调用 open”当成天然可复用已销毁对象。

### 待确认修复方案

1. 协调第 1 组共享写集后，统一一个活动内各控制器的创建、更新、清理边界。比较“按稳定身份维持控制器并更新活动快照”与“完整重建一组控制器”的影响，防止销毁后复用及闭包读取旧授权/课程信息。
2. 统一关闭活动时允许的操作及 UI 提示，核对服务端约束；不要只禁用按钮而留下重开后的生命周期缺陷。
3. 不通过自动刷新页面、清空待确认指针、新建活动或重复派发来掩盖问题；恢复继续核对原请求身份。
4. 回归至少覆盖：关闭→重开→运行；关闭状态操作边界；有草稿/待处理动作时关闭与恢复；返回首页重入和刷新；不重复执行、不覆盖新草稿。修复前先用最小测试固定已复现的行为，再做真实 Chrome 复验。

首轮建议写集：`ActivityReferences.tsx`、`AluExperimentTool.tsx` 及必要的生命周期回归；`LearningApp.tsx`、动作队列实现只有确需改变时才纳入。共享活动、对话和动作控制器需协调。后续用户已明确授权修复重开后等待问题，实际最小写集和验证见第 7 节；其他建议没有自动进入实施范围。
