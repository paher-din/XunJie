## 1. 任务目标和授权方式

围绕首页课程与任务、学习工作区的 Agent 引导与学生求助、ALU 课程组件，完成学生从进入到交付作品的真实使用验收；找出原设计与实际行为的差异，打磨 UI 和体验，按批准的方案补齐已有范围内的功能。

负责人本轮要求优先于旧实现。先讲清现状和架构，再提出针对性修复；不能把现有代码当作不可改变的设计，也不能把规划中的全部功能都当作本次欠账。

**2026-11-10 最新执行约定：** 功能对齐/优化先交付“原预期实现、实际实现、gap、对应优化方案”，形成可讨论版本后及时群内同步、约会讨论，确认后实施。独立 UI 可同步推进；第 2 组 Agent 输出 UI 必须等待第 1 组完成，再复用同一套组件与呈现约定，即使文件不冲突也不另行实现。该约定不撤销已单独授权并完成的 SF-01。

执行分以下状态：

| 状态 | 可执行工作 | 进入条件 |
| --- | --- | --- |
| 现状核查与体验 | 只读代码/issue、环境诊断、在获准开发环境复现、人工体验支持、记录差异、拟方案 | 用户开始执行本任务后；环境操作遵守对应 skill 和既有授权 |
| 独立 UI 打磨 | 课程入口、材料阅读布局、ALU 自身 UI 的呈现优化、对应回归和截图 | 已记录现状、明确写集；不改变业务语义；偏离设计规范须先确认 |
| Agent 输出 UI 接入 | 将第 1 组完成的统一输出组件接入课程场景，补上下文适配和验收 | 第 1 组已有可用交接提交、实际组件与接口；不得先做平行实现 |
| 功能修复 | 业务流程、数据、接口、权限、模型/工具行为及恢复语义的修改 | 该项方案经负责人讨论确认，记录决定及范围；已有确认不重复索要 |

初次使用本说明时，**先完成第 5 节阶段 A 的现状报告和方案草案，不默认开始功能实现**。后续收到继续执行或既有确认时接续相应阶段。群消息、issue 评论、PR 发布等外部动作按用户的具体授权执行；仅生成待发送文案不等于已经同步。

## 3. 范围与跨组边界

### 本组负责

- 首页课程和任务的查找、开始、继续、状态说明、空态/失败态和导航。
- 课程工作区的目标与材料、编辑与自动保存、固定引用、问题草稿、运行结果、离开/刷新/重开体验。
- 课程内 Agent 的真实求助、依据读取、工具结果说明、明确提问与回应、运行中补充/排队、停止/继续及已有引导呈现。
- ALU 真实编辑、编译诊断、单次观察、虚拟板、全量检查、预测比较、解释修订、波形和引用。
- 已交付 Skills/工具/资料/PDF/生成教学内容在上述课程旅程里的使用；不扩大到新扩展系统。
- 核实并验收本轮获准的作品交付终点，以及本组改动影响的恢复与连接路径。

Agent 输出 UI 交接需拿到可用提交、组件实际位置、输入/事件接口、已支持状态和运行示例。以同一组件或现有公共入口复用，不复制出课程专用分叉；不预造第 1 组尚未确定的 API。接入后核对课程上下文、固定引用定位、工具结果来源和已有卡片状态。交接前继续收集案例、梳理数据适配，不新增临时输出 renderer。

### 阶段 B：把问题分成可审查的小方案

每个功能问题先用“原预期实现 / 实际实现 / gap / 对应优化方案”四栏说明，再补下面的证据与实施细节。首批讨论稿及待发送群文案在 [人类方案第 10 节](student-flow-week-plan-2026-11-10.md)。优先围绕用户可见的一项行为组织，不先拆成零碎文件任务：

```text
问题编号和学生场景：
版本/环境/课程发布：
原预期及依据：issue 条款、负责人确认或现行规范
实际实现：真实源码与本次操作结果；未测项单列
gap：原预期和实际之间的具体差异；证据不足则标待确认
复现：最小步骤、预期、实际结果、截图/日志
代码现状：页面 → 接口 → 所属模块；已证实原因与待证实假设
分类：UI / 功能漂移 / 环境与数据问题 / 未来需求 / 待确认
对应优化方案：行为如何改变，复用什么，清理什么；备选与取舍
边界：不涉及哪些相邻功能；是否触及第 1 组
写集与负责人：文件/契约/数据变化，兼容与恢复影响
验收：正常、失败、恢复、回归；人工体验步骤
优先级与粗估：影响、工作量、依赖；范围变化后更新
决定：待讨论 / 已确认，确认人、时间、约定和未决点
群同步：草稿待发送 / 已发送；实际消息位置、讨论时间或待约
```

优先级建议：P0 为数据丢失/串用、关键主线阻断、错误成功回执或结果归属；P1 为主要操作难完成、错误不可恢复、求助或来源明显误导；P2 为不阻断的密度、间距、动效和细节。它们是分类标准，不代表已发现这些缺陷。

可讨论方案完成后及时提供群同步稿，包含四栏摘要、要决定的事项和证据位置，不等实现完成才同步。没有原设计依据的交互选择标“方案建议”，环境未就绪标“待补验”，不包装为已经证实的实现漂移。未获具体发送授权和目标群时由人类发送；草稿不等于已同步，预定会议不等于方案已确认。会议确认前继续核查、证据整理和独立 UI 优化；不实施未确认功能或抢先实现 Agent 输出 UI。

**交付终点决策必须单列：** 若已有获准接收方，沿其接口验收真实接收、固定版本与重读；若只是正式入口遗漏，提出小范围接线方案；若缺完整 WP12 能力，提交范围冲突由负责人决定。只有负责人明确认可某个已有导出/交接方式时才能把它作为本轮终点，不自行新增替代提交流程。未决时继续其他工作，最终如实写“交付终点尚未验收”。

### 阶段 C：实施已确认项并逐项复验

- 按交接顺序接入第 1 组共享改动；第 2 组两人各有明确文件写集，共享页面由指定集成人收口。

- 重大 UI 改动保留同条件的修改前后真实运行截图；不得使用生成图、旧交付截图或修改截图来充当本次对照。

证据只保留本次修复、PR 审查和人工复验会用到的最小内容，可归入现有方案/问题记录和必要附件，不为每个步骤另建报告。必要记录包含实际命令、退出码、提交、课程/组件版本、失败与结果；模型问题保留脱敏的 Run/Command/来源关联。工具如已支持可用调试包交接，先按 skill 核对能力，不额外建设 WP13。凭据、token、账号密码、私有邀请及无关学生内容不得进入代码、日志、截图或提交。

收尾只停止本次临时进程、清理本次已无消费者的临时环境/日志/包。保留运行中、待验收及安装元数据仍引用的资源，保留用户既有文件与本次同步备份；不能直接运行全量 `clean:verification` 把它们一并清掉。重大 UI 前后截图及必要问题证据有明确交付用途，按要求保留。

## 8. 每次汇报和最终交付格式

进展汇报简要说明：已证实什么、本次做了什么、下一步解决什么、需要团队决定哪一项。不要把假设写成缺陷结论，不只报“测试通过”或“已优化”。

最终 PR/交付必须包含：

1. 问题与行为变化：对应学生步骤、原预期与修复后的可见行为。
2. 范围和协作：本次文件/模块、依赖的第 1 组交接、功能方案确认记录、替换/清理内容。
3. UI 对照：重大 UI 变化的原因、影响和真实运行界面前后截图。
4. 工程检查：命令与结果，失败/跳过/未执行分别列出。
5. 浏览器与真实链路：平台、Chrome、连接/数据路径、真实模型和 ALU 执行结果。
6. 人工体验：谁亲手完成了哪些步骤、发现和复验的问题；与 AI 自动浏览器操作分列。
7. 教学效果：实际观察或未评估，不外推。
8. 剩余工作：未确认功能、未测路径、阻塞、负责人，以及最终交付是否真正完成。

最终完成标准是：本批批准范围内的改动可用、关键问题已复验、人工全流程记录齐备、依赖与未完成部分透明。若教师提交等终点仍待决，只能交付阶段成果；不得把后续范围偷偷加做，也不得把阶段成果称为全流程已通过。
