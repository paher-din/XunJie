# 第 2 组本周工作安排：学生学习全流程

适用时间：2026 年 11 月 10 日起的一周，11 月 11 日更新。当前在 `codex/student-flow-polish` 上推进，已合入主线 `ab918bce` 并保留本地修复和 UI 改动。按第 2 组两人协作安排，具体同伴与投入时间待团队落实。配套文件：[给 AI 的执行说明](student-flow-ai-brief-2026-11-10.md)。

你的主要任务是：**亲自走通学生从首页找到课程、进入工作区、学习和求助、完成 ALU 实验，到交付作品的过程，找出不好用和实现偏离的地方，再推动修复、复验。** 这周先建立可信的体验记录，完成最影响学习的修复，不按代码量或关闭任务数衡量进展。

**负责人最新约定（2026-11-10）：** 功能对齐和优化先出方案，写清“原预期实现 → 实际实现 → gap → 优化方案”，方案完成后在群里同步、约时间讨论，确认后再实施。UI 可以并行推进；但第 2 组涉及 Agent 输出的 UI 必须等第 1 组做好后复用同一套。此前单独授权且已修复的 SF-01 保留。

**日常推进看第 11 节的可勾选清单。** 任务状态统一维护在那里；原预期、源码和验证依据见 [开发计划核对报告](student-flow-design-coverage-2026-11-10.md)。

## 1. 你具体负责什么

| 工作块 | 你需要实际操作、判断的内容 | 完成后应留下什么 |
| --- | --- | --- |
| 首页课程与任务 | 能否找到自己的课程、理解任务目标、开始或继续学习；任务状态、返回路径是否可信；空白、加载失败是否说得清楚 | 首页问题清单、必要的 UI 优化、真实开始与重开记录 |
| 学习工作区 | 材料、当前作品、运行结果是否容易找到；编辑、切换文件、刷新、离开再回来是否顺畅且不丢内容 | 工作区体验问题、修改前后截图、保存与恢复复验记录 |
| Agent 引导与学生求助 | 能否引用代码、材料、波形和结果提问；回答是否依据当前问题；等待、停止、补充、回答 Agent 的问题是否清楚 | 一组真实求助案例、错误或不适点、修复方案和复验结果 |
| ALU 课程组件 | 阅读规则、修改代码、运行、操作虚拟板、看波形、做预测与比较、理解检查反例，是否真正可用 | 至少一条“失败 → 求助 → 自己修改 → 再验证”的完整记录 |
| 作品交付终点 | 核实这轮正式产品究竟支持怎样交付，区分作品已保存、实验已通过和教师已收到 | 明确的交付边界；现有路径的验收，或提交负责人决定的缺口 |

典型主线是：**首页 → 课程与任务 → 看目标和材料 → 编辑 ALU → 预测或自由实验 → 看结果并求助 → 自己修改与验证 → 交付 → 重开核对。** 预测和自由实验允许往返，不设计强制答题或“全部通过才能继续”的新门槛。

## 2. 最新代码已经具备什么，先查哪里

**按合并后的代码验收。** 主线已有 ALU、Skills、PDF、资料检索及交互教学卡片，这次又合入开发学校公网接入、工作区模型选择、个人技能库和统一通知。课程界面沿用这些能力。第 1 组的 Agent 输出组件以实际交接为准。[实施索引](../student-agent-implementation/README.md)

代码核对后，首轮体验优先看四点；以下先列核查方向，已实际复现的问题见后面的“本轮体验更新”：

- **开始与继续是否容易区分：** 课程入口先选发布版本再开始活动；已有活动从“我的学习活动”继续。首页推荐的是“最近创建的进行中活动”，不是最近操作的活动。先体验是否符合学生预期，调整排序属于功能方案。
- **课程任务是否好找：** 首页已拆成独立组件，但课程任务列表和发布详情仍在共享的 `LearningApp.tsx` 中，改这里需与第 1 组协调。
- **引导是否及时又不打扰：** 已有的工作区引导会在 Agent 等待回答、对话面板收起时提示回应；先验收这条真实路径，不扩大成完整主动教学/画像系统。
- **“最终交付”到底是什么：** 正式工作区已有“关闭/重新开始活动”，这不等于教师收到作品。旧任务页有另一套“提交与反馈”，正式链仍将教学交付归给 WP12。尽早确认本轮终点；不能用关闭活动、自动保存或检查通过代替提交成功。[正式与旧版入口说明](../../apps/web/README.md)

## 3. 做到哪里，哪些交给别人

- **第 2 组主责：** 首页课程/任务、课程工作区、课程内求助与引导、ALU 使用、这条链上的保存恢复与作品交付边界。
- **第 1 组主责：** 设置页、学校账号连接、模型配置、Skill 添加管理、侧栏自由 Agent 对话。你需要验收它们进入课程后的效果，并把配置或通用对话问题交给第 1 组。
- **Agent 输出 UI 的明确依赖：** 课程内回答、流式输出、工具结果、引用及暂停/错误等输出呈现，等第 1 组完成后接入同一套组件；不先做一套课程专用样式。等待期间可以查功能差异、收集真实输出案例和整理接入需求。
- **已有能力也要查：** 课程内使用 Skills/工具、PDF 引用、生成教学卡片已经有实现，属于体验核对范围，不应误删为“未来功能”。
- **不自动加做：** Flights/R 数据分析，产品中的 MCP/Plugin/MCP Apps，以及尚未开展的教师课程创作、完整连续引导/画像、完整提交反馈系统。工作区已有的引导和明确回应继续验收；发现后续能力缺口提交讨论，不自行扩成新工作包。[本轮实施边界](../student-agent-implementation/student-agent-implementation-overview.md)

## 6. 你亲自体验时，至少做这几件事

1. 用真实学生账号找到 ALU 任务，只按界面说明开始，记下第一次犹豫、找不到或不理解的位置。
2. 阅读规则，编辑作品并切换文件；刷新、返回首页再进入，检查代码和草稿还在。
3. 跑一次会失败的实验，读诊断；再操作虚拟板、波形和全量检查，确认自己知道结果对应哪份代码。
4. 引用失败代码或结果求助，让 Agent 解释；自己修改后再运行，确认旧结果没有被当成新代码已通过。
5. 记录一次预测和理由，再运行比较、写解释；也试一次直接观察，界面应如实区分。
6. 试一次 Agent 提问后的明确回答、生成中补充、停止与重开；试一次课程材料/PDF 引用和教学卡片重开，记录实际能力。
7. 在受控条件下断开相关连接后恢复，检查输入和原结果；按已确认的交付方式完成终点，并回来核对。

AI 可以准备数据、分析日志、操作浏览器和补自动化回归，**这些都不能替代你和同伴亲自操作**。额外找一位不熟悉界面的同学试用有帮助，但不是本周新增硬门槛。人工体验能发现可用性问题，不直接证明教学效果提升。

## 7. 哪些可以直接改，哪些先讨论

文案、间距、排版、层级、焦点等 UI 优化，在既定设计规范内可以落代码；使用 [DESIGN.md](../../DESIGN.md) 和 [正式组件库](../../packages/ui/README.md)，先看组件覆盖清单与实屏示例。可同时运行旧版预览作设计参考。需要新组件时按需查 Astryx 或 shadcn，适配后纳入 `@xunjie/ui`；Impeccable 可选，不为使用工具而重做页面。

| 现在怎么处理 | 具体范围 |
| --- | --- |
| 可以先做 UI | 首页课程/任务视觉层级、现有按钮文案、材料排版与阅读空间、ALU 自身输入/波形/检查区布局；不改业务行为、不碰冲突写集 |
| 先出功能方案 | 活动选择与排序、求助可用性与恢复策略、状态判定、保存/引用/交付语义；按原预期、实际、gap、方案列明后群内讨论 |
| 等第 1 组再接入 | Agent 回答和相关输出状态的呈现；复用交接后的实际组件和接口，不复制出第二套实现 |

例如，材料宽度和字号可以先改；换 Markdown 渲染器若影响选文引用，需把引用映射作为功能方案。实验提示措辞可先整理；如果要改变状态判定，也先讨论。

改变业务行为、状态流转、数据保存、工具权限、求助策略、课程规则或交付含义的修改，即使只动一个按钮，也属于功能方案，先同步讨论。偏离 DESIGN.md 的 UI 方案也先说明差异并确认。不要让 AI 把“功能漂移”当作自动获得重写授权。

功能方案每项先用四栏讲清楚：**原预期实现、实际实现、gap、对应优化方案**，再附证据、影响和验收方式。没有找到原设计依据时标“待确认”，没有跑通的环境标“待补验”，不直接写成缺功能。方案形成可讨论版本后及时发群，不等代码完成才同步；讨论确认后再实施。群消息由你发送，AI 提供文案；已有明确发送授权时按指定群执行。
