- **L21**：2026-10-27 模型选择答复：学校空间内，学生始终可以自行选择个人模型，不以学校管理员允许为前提。学校提供的模型服务与学生个人模型均为可选来源；更换模型不改变学校课程、作品、学习活动或交付的空间归属，也不扩大可用课程组件和材料范围。连接、凭据保存及运行切换按[模型连接契约](references/2026-10-27-overall-architecture-proposal.md#学生的模型选择与凭据边界)设计，不将此答复扩张为学校承担个人模型费用或自动共享个人空间数据。
- **L22**：2026-10-27 设置价值原则：负责人指出，应先判断哪些选择能给学生带来实际价值，不将没有必要或没有收益的设置交给学生，以免增加使用门槛。此前“学校提供默认组合，学生自行选择 Agent 和完整学习数据放在本机”的建议据此撤回，不再作为等待二选一的问题。已明确的是设置价值原则；工程据此建议将 Agent/数据服务位置留在部署配置，由产品按配置完成连接，学生保留模型选择、主动引导等有直接使用价值的控制。L18 的本地/云端可组合能力与 L21 的个人模型选择继续成立，不能把本次答复误记为用户选择了学校集中部署或禁止本机组件。
- **L23**：2026-10-27 最终设计要求：负责人针对“首版采用自有持久 RunDriver”指出，要的是长期设计，后续遇到其他问题再补充、更改，并明确“我要最终设计”。本轮据此按长期适配性重新核对内核，定稿完整运行责任、持久等待、部署单元和演进契约；不保留先用简化内核、以后再换完整方案的预设。此答复明确设计目标，不冒充负责人逐项认可某个内核或已经验收实现。

- **L27**：2026-10-27 个人扩展答复：学校课程中允许学生自愿添加个人 Skill/MCP，例如检索自己的笔记；须遵守课程规则，不扩大课程材料与操作权限，普通学习流程不要求配置这些扩展。个人扩展与课程发布能力分开绑定，模型选择自由保持独立。

## 最初 idea 中需要保留的产品原则

教师主导教学设计与最终判断；Agent 提供主动、引导式帮助，让学生参与思考；项目完成与知识掌握分开判断；个性化需要可持续维护的学习画像；课程组件与教学产物可复用。教师设计 Agent、教学分析 Agent 与跨学生案例库保留为产品方向，本轮不展开其实现。

I0 中的“零适配门槛”按 L8 拆成可验证的边界：教师可复用或借助 Agent 创建新工具，现有执行能力内的新依赖通过工具与环境装配接入；超出已有接口或执行能力的机制才需要适配。配置与检查应由产品和 Agent 协助，不能把“可配置”变成要求教师手写清单或自行集成。架构不能承诺自动理解所有外部工具或无需适配就支持任意系统能力。

L9 明确首条数字逻辑活动是样例，不能将其预测、仿真、时长或只解释不改代码的规则推广到所有课程。L10 明确课程准备由教师与 Agent 协作，学生端默认轻度主动并尊重学生选择；帮助体验与主动性要根据真实反馈改进。L11 已确认学生设置与轻量反馈方式；L12 已确认无扰检测首版采用活动证据、规则与时机控制。体验满意、任务完成与知识掌握不合并成同一种结果。[原始研究](references/2026-10-23-unobtrusive-guidance-evidence.md)与[开源实现调查](references/2026-10-23-unobtrusive-guidance-implementations.md)提供选型依据，具体阈值、标签质量和算法效果仍需验证。

## 第三轮决定与架构重评

**Q7 用户决定：运行方案由教师设计，优先本地。** 原提问把执行位置交给学生选择，不符合产品意图，现已撤销该建议。教师/教师 Agent 先评估本地环境能否满足课程；仅对无法满足的能力配置远端资源。学生按发布的课程方案使用，平台负责设备检测和方案内调度。

教师决定运行规则，不需要预先指定每位学生的物理节点。设备不符合要求时，平台引导环境准备；只有课程已配置相应远端替代路径时才能使用，不能静默把任务转上云或展示节点选择器。

**Q8 用户委托技术判断。** 用户没有对五条旧方案作统一批准，而是要求自行判断是否合适。本轮据此确定 P1—P5，修正教师运行方案、统一 UI/状态宿主、限制自研范围与本地交互路径；不再把 SDK 选择或整体技术结论留作等待用户勾选的事项。

当前研究见[执行位置研究](references/2026-10-18-execution-topology-research.md)。它证明相关机制有边界，不代表本项目已通过跨平台兼容或性能验收。

## 开发协作与产品运行边界（L7）

当前共享数据和部分服务的云端环境服务于团队开发复现，应保持尽量小的范围；它不决定产品的应用服务、执行节点或数据最终放在哪里，也不锁定产品数据库和资源存储。产品仍按 Q7 由教师设计课程运行方案、尽量学生本地执行。P1/P5 已按长期目标明确运行与部署选择，L24 指出的完整 Agent 能力缺口已通过能力契约、交互设计与完整请求走查补齐，组合设计继续采用自有持久 RunDriver。

L18 进一步明确：产品部署方案由使用者或组织决定，首版即需要各部分可本地或云端组合；课程运行方案仍由教师设计。这是两种不同决定，不能把前者收窄成学生只连接统一后台，也不能把后者改成学生挑选实验节点。

开发复现需能对齐代码 commit、工具链与配置版本、相关数据/schema/seed 版本，并记录输入、复现步骤、预期与实际结果；共享环境还需避免成员测试数据和任务互相污染。DEV1—DEV2 已进一步明确隔离方向与工具需求，开发工具已按 #126 实施，实际能力与验收边界见[当前交接](references/2026-10-24-team-development-handoff.md)。运行位置与部署候选见[架构正文](student-agent-architecture.md#运行位置与部署组合)，课程运行原则见 [ADR 0001](adr/0001-teacher-owned-course-execution-plan.md)。

DEV1 将开发体验细化为本地前后端均可修改，DEV2 认可本地全栈与独立可写数据副本作为默认，共享版本化的数据基线和问题复现场景；云端应用保留作集成与演示，另提供可选的本地前端连云端后端模式。具体理由、源码约束和使用边界见[开发协作方案](development-collaboration.md)。

DEV2 进一步明确开发工具面向开发 Agent，并与普通用户的安装和运行隔离。工程建议用独立 CLI 执行确定性的环境与数据操作，项目 Skill 提供调用说明，通过独立文件存储传递带版本和摘要的场景包；具体设计见[开发协作工具](development-tooling.md)。这些开发设施不决定产品部署位置；工程、实机连接、真实执行与教学效果分别报告。

DEV3 将模式切换、成员接入和运行管理纳入同一开发体验。服务器实测为 2 vCPU / 2 GiB / 40 GiB、3 Mbps 公网出口，当前业务健康；据此建议大文件直达对象存储、CI 承担构建，ECS 保留共享业务与轻量开发授权。切换模式不隐式同步数据或部署，基线更新保留旧副本。详见[成员接入与运行策略](development-access-operations.md)和[服务器核查](references/2026-10-23-development-server-assessment.md)；资源预算与五人窗口已完成独立验收，具体范围见当前交接。

DEV4 后形成轻量开发接入服务，最初以邀请自动登记；随后按负责人本轮要求加入 GitHub 固定用户 ID 名单和网页设备授权。现行成员使用 Skill 与 CLI 自动完成接入，维护者通过原 owner 通道管理权限。该流程与教师产品架构隔离；当前工具、旧入口退役及恢复线索见[开发协作工具](development-tooling.md)和[当前交接](references/2026-10-24-team-development-handoff.md)。

GitHub 核对表明，[本地优先执行](https://github.com/paher-din/XunJie/issues/114)面向学生课程实验；[重构迁移与验收](https://github.com/paher-din/XunJie/issues/120)已包含开发复现与隔离要求。开发工具可以独立实施，本地开发部分现在可以开始，不以产品设计票关闭作为整体前置。DEV5 要求的[正式规范与实施子票](https://github.com/paher-din/XunJie/issues/126)已按负责人确认的测试边界和拆分发布，具体依赖以原生关系为准；旧实现清单统一见[工具设计](development-tooling.md#旧连接实现配置与说明的替换清理)。

已建立 [xunjie-development](../skills/xunjie-development/SKILL.md) 作为开发协作的唯一项目 Skill，根规范提供条件入口，工具事实集中在使用说明及实际脚本。它承接 DEV2、DEV4 的明确要求，用于持续发生的开发启动、接入与复现交接；没有新增 CLI 或复制工具实现。验证结果在本轮变更记录中记录，不以 Skill 文件存在宣称未来环境能力已经可用。
