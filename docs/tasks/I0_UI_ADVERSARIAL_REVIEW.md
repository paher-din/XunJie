## 1. 从问题本质建立判据

当前问题是：在 A/C 正常业务宿主和部分初始化交接未齐时，前端接入成员怎样交付可以迁入正式应用的工作，并让其他 Agent 无需重新猜业务规则就能实施。

由此得到五条审查判据：

1. **作品事实必须可信。** 页面说已保存、快照或已停止时，必须有对应事实；正文和引用不能在异步、刷新或冲突中悄悄改变。
2. **准备工作必须可回用。** Mock 验证要覆盖真实客户端，不能造出将来不得不替换的第二套业务逻辑或没有来源的返回字段。
3. **任务必须可完成。** 前置输入、权限、状态和验收必须相容；不能把尚待决定的必要条件藏在已就绪状态后面。
4. **范围必须是一条可验证行为。** 导入、编辑、确认保存和运行要尽早形成最小路径；错误恢复、历史和后续报告可逐步增强。
5. **正式依赖按能力交接。** 身份/读取/保存/执行各自需要什么就交什么，不因为部分缺口要求全包齐备，也不把未交付字段填成事实。

## 3. 必须修正的发现

### R-01 / P1：必需的实施前置仍未确定，却把所有任务标成 ready

**位置：** [PREPARATION §1](I0_UI_PREPARATION.md#1-使用入口与授权状态)，[02 状态及验收](I0_UI_02_EDITOR_DRAFTS.md)，[SPEC Testing Decisions](I0_UI_SPEC.md#testing-decisions)，[07 验收](I0_UI_07_BROWSER_HANDOFF.md)。具体锚点：PREPARATION 行 16，02 行 7/24，SPEC 行 80，07 行 20/22。

文字一面说新的 IndexedDB 实际建库范围待确认、浏览器测试还是建议，一面强制真实 IndexedDB 和 test:e2e 全部通过。01 的最小浏览器检查也依赖尚未固定的测试办法，现有来源工程只有 Vitest。`ready-for-agent` 被重新定义成“文档可交接”，失去了区分可以实施与尚待前置的作用。

**反例：** Agent 完成 01 后领取 02，必须建新库才能完成验收，却发现文档自己仍保留该范围的确认；领取 07 又发现必需的 E2E 框架只是建议。Agent 只能重新询问、留下半张任务，或把 ready 错当这些前置已经解决。

**修正：** 分开记录“文档定稿”和“执行状态”，列出准确的非 ticket 前置及其状态。确定本批可用的浏览器检查方式；新增依赖和建库按真实授权记录处理，不能将未答复记为同意。已有目录/Monaco/拆分决定不重问。未满足必要条件的任务标 blocked 或具体条件待落实，条件具备的部分照常推进。

### R-02 / P1：准备模式的运行方式没有定义，HTTP Mock 测试不能自动形成可用的开发场景

**位置：** [SPEC Solution](I0_UI_SPEC.md#solution) 行 15/64～65，[01](I0_UI_01_IMPORT_C_ENTRY.md) 行 29/31/33，[03](I0_UI_03_CONFIRM_SNAPSHOT.md) 行 17～26。

计划要求准备场景可用，03 要有保存/快照客户端，却只指定浏览器测试里的 HTTP 响应注入。没有指定普通 `npm run dev` 的准备请求由谁响应、状态在哪里、刷新读回如何与写命令一致，也没有说明真实与准备 transport 如何选择。来源 `mockAdapter` 只有原演示/消息接口，没有 C2 作品命令；默认后台 main 只启动健康应用。

**反例：** 实现者在 Playwright 中拦截 sync/snapshot，测试全绿；独立打开准备工作区点击保存，实际 `/api/attempts/.../sync` 仍无服务。另一个实现者为补展示临时新增“假保存逻辑”，测试与真实客户端走两套路径，两种实现都可能满足现在的分散文字。

**修正：** 先确定准备能力是“仅自动化测试可用”还是“开发启动也可交互”，据此限定独立交付承诺。若需要可交互准备模式，01/03 明确同一客户端的受控 transport/fixture 入口、状态归属、读写一致性、刷新语义和模式切换；使用与真实接口相同的序列化投影，不实现第二套业务后台。真实请求失败不能触发隐式 Mock 回退。

### R-03 / P1：运行输入比较的验收超出了现有公开 Run 投影

**位置：** [06](I0_UI_06_RUN_RESULTS.md) 行 19/25，[SPEC](I0_UI_SPEC.md) 行 46/50/75，[PREPARATION](I0_UI_PREPARATION.md) 行 104～107。

06 要求两次运行能比较参数、恢复运行的发生条件，但 [readWorkspace](../../apps/teaching/server/workspace/commands.ts) 行 155～158 只返回 runId/jobId、snapshotId/hash、mode、profile/image 与 diagnostics；GET Run 复用该投影。没有公开 entryFileId、input 或 inputHash。当前页自己刚发送的参数可以留作本机请求事实；换浏览器或本机缓存丢失后不能据此恢复历史参数。

**反例：** fixture 为 GET Run 加上 input，浏览器比较通过；真实服务交接后拿不到这些字段。若回填当前控件值，会把旧运行误标成新输入；若 Agent 改服务端返回，则越过“不改变共享契约”的任务范围。

**修正：** 为每个展示字段列来源和缺项行为。已知本机请求标为其实际来源；历史参数不可回取时明确 unavailable，不能猜。若确需跨浏览器完整比较，先提出最小投影差异交 A/C 确认，作为对应验收的明确前置。fixture 必须与当前公开投影一致。

同时必须固定既有裁剪语义：[result-files](../../apps/teaching/server/workspace/result-files.ts) 行 14 的检查产物返回 redacted；[runDiagnostics](../../apps/teaching/server/workspace/commands.ts) 行 226 的 check 只给 verdict/failureKind。将 `redacted`/`unavailable` 当空成功或填入私有正文同样不合格。

### R-04 / P1：迟到响应的隔离维度缺少恢复代际和当前加载轮次

**位置：** [03](I0_UI_03_CONFIRM_SNAPSHOT.md) 行 24，[04](I0_UI_04_RECOVERY_CONFLICTS.md) 行 21～22，[SPEC](I0_UI_SPEC.md) 行 66/71。

检查请求、模式、账号和 Attempt 能拦住不同对象，不能拦住相同账号/Attempt 的旧加载或旧恢复代际。停止旧代际重试也不等于已发出的旧 ACK 不会到达。规范没有要求在每次 await 后核当前工作区上下文，相关浏览器验收只覆盖旧请求被拒绝和切换账号。

**反例：** g1 的保存已成功，ACK 在途；后台恢复为 g2，当前页已载入回退后的 head；g1 ACK 随后到达。模式/账号/Attempt/request 归属都合法，若应用该 ACK，就把 g2 不存在的作品重新标为服务已确认。相同账号退出/重新进入同一 Attempt 也会遇到旧加载覆盖新加载。

**修正：** 为当前工作区明确加载轮次/上下文失效规则，把受信代际纳入异步结果接纳条件，旧上下文只保留历史事实，不能改当前确认基线。增加“g2 已重读后 g1 ACK 到达”和“同身份同 Attempt 两次读取逆序返回”的浏览器反例。无需改变服务端契约。

### R-05 / P1：Monaco 原文本保真没有可实施办法，默认 model 不能当字节权威

**位置：** [SPEC](I0_UI_SPEC.md) 行 60～61，[02](I0_UI_02_EDITOR_DRAFTS.md) 行 17/26，[TECH 原字节与范围契约](../product/TECH_DESIGN.md#41-共同对象引用) 行 162。

规格正确要求原 EOL/正文不变，但选择 Monaco 后没有明确权威原文与显示 model 的关系。它的核心文本缓冲默认规范化混合换行，API 还单独处理 preserveBOM。仅验证纯 CRLF 与非 BMP，不能证明混合 LF/CRLF、单独 CR、BOM 及其范围映射不会在打开/保存时变化。

**反例：** 服务器保存 `a\r\nb\nc`，只打开文件、不编辑；实现直接用 model.getValue 生成同步正文/摘要，混合换行可能已经变成统一换行。浏览器此时产生学生未发起的正文差异；原快照 UTF-16 引用也可能与显示行列不一致。

**修正：** 在锁定版本上先验证最小原文往返，不改编辑器选型。规定原始文本的权威位置、显示/编辑转换及不能精确映射时的处理；补混合 EOL、CR、BOM、末尾空行、非 BMP 的“打开未编辑→保存/快照”和实际编辑反例。不能改产品基线去迁就默认规范化。

一手证据：[Monaco ITextModel](https://microsoft.github.io/monaco-editor/typedoc/interfaces/editor_editor_api.editor.ITextModel.html)、[编辑器核心文本缓冲](https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/model/pieceTreeTextBuffer/pieceTreeTextBufferBuilder.ts)的 create/finish。以上对未来所选版本的适配风险是依据源码作出的判断，尚未实测该版本。

### R-06 / P2：本机 ACK 落盘与创建映射的崩溃一致性没有验收

**位置：** [03](I0_UI_03_CONFIRM_SNAPSHOT.md) 行 18～20/25，[02](I0_UI_02_EDITOR_DRAFTS.md) 行 23～25，[04](I0_UI_04_RECOVERY_CONFLICTS.md) 行 18/25。

文档规定 POST 前保存原命令，未定义 ACK 到达后创建映射、确认基线、最新草稿关联、待确认命令状态应如何一致落盘，也未定义 clientSeq 在多标签/刷新下的分配和不复用。C2 同时按幂等键与 clientId/clientSeq 去重；正文保留与两个标签的 CAS 并不能自动解决命令身份碰撞。

**反例：** 服务创建文件成功，本机先标命令完成，尚未保存 clientFileKey→fileId 映射就崩溃；刷新只剩“新建草稿”，下一次保存按新命令再次 create。反向落盘次序又可能让重放后的旧正文覆盖正在编辑的草稿。两标签共用 clientId 且各自分配同 seq，会把两个不同操作送入同一去重槽。

**修正：** 明确 ACK 应用的事务边界、可重复接纳和原请求恢复规则；采用能证明不复用的 clientId/seq 分配规则。增加 ACK 本机提交中断、刷新重放、两标签同时发不同命令的反例，不只验证网络丢 ACK 和本机正文写入冲突。

### R-07 / P2：C 工作区缺少 UI 能力差异与接入落点，导入后不会自然出现

**位置：** [01](I0_UI_01_IMPORT_C_ENTRY.md) 行 29～30，[02](I0_UI_02_EDITOR_DRAFTS.md) 行 21～22，[PREPARATION](I0_UI_PREPARATION.md) 行 60。

固定来源的 WorkspacePage 行 477 只为 `counter` 渲染 CenterToolArea，其他任务显示工具包待接入；中心工具只有 design/board/wave，没有文件导航、确认保存、快照/运行结果与冲突入口。现有样式和容器可以复用，但“沿用界面、增加必要交互”没有明确哪些能力已交付、哪些要扩展、由哪个 ticket 和角色落实。

**反例：** 01 仅新增 TextScope 任务卡，进去仍是工具包占位；02 为放多文件新造一个旁路工作区，03/05/06 再各自设计按钮/面板，最终违反围绕实际 UI 对接的边界或发生返工。

**修正：** 在任务内补最小 UI 能力差异表，说明 C 工具区怎样进入既有容器、现有槽位如何复用、缺失操作由谁补交或确认。先明确差异及协调，再实现必要交互；不在审查阶段另设计页面、布局或视觉。01 的独立验收须说明 C 入口交付的是可用容器还是有标识的占位。

### R-08 / P2：任务粒度和外部阻塞关系没有对应独立行为闭合

**位置：** [PREPARATION](I0_UI_PREPARATION.md) 行 126/142～144，[04](I0_UI_04_RECOVERY_CONFLICTS.md)，[06](I0_UI_06_RUN_RESULTS.md)，[07](I0_UI_07_BROWSER_HANDOFF.md) 行 30。

04 合并网络未知、多标签、服务 CAS、代际恢复、身份切换、暂停/终态；06 合并运行参数、作业所有状态、可信检查、Report、下载、两次比较及故障恢复。它们是多条可独立演示的行为，不能只写“一个上下文”就认为粒度合适。并行共用写集已提示协调，这一提示是正确的，但 03 交接输出仍只有抽象名称，后续比较/恢复/运行容易各造状态。

此外，真实接入被统一写为 H-01～H-06 全齐后另起批次；登录/材料/Attempt 初始化的客户端准备没有 ticket 明确认领。现有 GET/POST 的已知客户端可先交付，未知入口按能力保持缺口。本人分配入口也不必先假定一定是新列表 API，可以是 A 提供的获准入口；不能把便利的完整列表误设成所有真实联调前置。

**修正：** 先形成“导入→真实编辑/草稿→单次确认保存/快照→单次 Core 运行与结果”的最小准备路径；复杂恢复、历史/比较、检查/产物按独立行为分批。给每批列必需输入/交接和可观察输出，明确初始化客户端及资料阅读的负责范围。真实读取、保存、运行各自按所需 H 条件接入，不等全部条件或整个其他模块完成。具体重拆需保留已经确认的业务范围，不自动改排程或派 A/C 新任务。

- A/C 宿主、分配入口、代际和执行交接未齐本身不是本批文档造成的缺陷。被指出的是如何避免它们导致准备实现失真或形成不必要的整包等待。
- 术语表和导入 ADR 未发现独立的严重业务语义错误；它们不能补足具体任务中的状态/契约空缺。
