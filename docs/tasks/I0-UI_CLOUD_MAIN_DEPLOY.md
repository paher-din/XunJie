# I0-UI：云端与远程 main 自动同步部署

日期：2026-10-15（Asia/Shanghai）。主责 UI / Robert，沿 `i0/ui-frontend`，在已有隔离 worktree 实施。

## 授权与依据

负责人明确要求：部署当前远程 main；以后合并 main 后同步部署，让成员刷新即可使用，并确保云端对应最新远程 main。本轮授权覆盖必要部署脚本、systemd 服务与定时任务、既有应用重启及部署配置；数据库、账号、公钥、证书、执行节点和个人模型资料沿原私有配置保留。

已读 README、根规范、PRD §5、MVP_SPEC M-10、TECH_DESIGN §9–10、[原云端接线](I0-UI_CLOUD_SHARED_ENTRY.md)和[双角色数据整理](I0-UI_SHARED_DEMO_ACCOUNTS.md)。适用 PRD-09/10、M-09/10、AC-10/12、NFR-01/03/06。产品与规划基线只读，汇总仍交获授权维护者。

可写：`tools/i0-cloud` 内通用部署脚本、相称测试及 systemd 模板、README、本记录。实际部署配置、版本回执和连接资料只在服务器及仓库外私有目录。本轮不新增业务接口、依赖或数据库 schema，也不初始化、迁移、覆写或恢复业务库。

## 最小方案与完成判据

复用既有发布目录、current 链接及应用服务。服务器每 5 分钟检查固定远程 main，既控制占用也避免公开 GitHub API 的匿名额度被每分钟轮询耗尽；可沿同一 service 手动立即触发。通过官方 API 与源码下载服务固定完整提交号和 Git tree，不保留全仓 Git 镜像。在临时目录以低权限身份按 lockfile 构建前端；后端沿原 Node 24 入口直接运行 TypeScript，只使用生产依赖。负责人补充要求云端轻量化，故运行包仅含页面产物、后端运行源码、生产依赖及原宿主入口；测试、证据、前端源码与开发依赖不进入发布目录，构建目录结束后清理，C/HDL 工具链仍只在成员电脑。构建期间保留原服务；切换前做 SQLite 一致备份，再原子切换整个发布目录并重启原应用。现有私有配置和持久数据不随发布目录替换，静态目录通过 current 引用同一版本。

构建结束再核对远程 main，若出现更新则不切换过时目标。切换后严格 TLS 检查 live、ready、首页与实际入口 JS；失败只回退应用代码和链接，不回滚业务数据。回执记录提交号、Git tree、前端产物摘要和实际状态。已有版本与原手工发布包保留，本轮不启用历史版本自动删除。

完成需同时成立：云端实际发布提交号等于最新远程 main；原教师/学生、课程与作品数据保留；健康及前端资源一致性通过；定时任务已启用并实际运行；重复同步不重启同版本；构建/健康失败不被记作最新部署。成员已打开页面需刷新，SSH入口沿原方式使用。

自动部署在服务器运行，不依赖本地 skill 或任何成员电脑在线；人工维护复用同一服务器入口，避免另一套部署实现。
