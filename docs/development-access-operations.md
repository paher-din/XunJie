## 当前工具入口

新成员在已发现项目 Skill 的编码 Agent 中只需调用 `$xunjie-development`。Agent 按[首次上手 reference](../skills/xunjie-development/references/onboarding.md)检查配置、依赖及本人身份；已有授权直接复用，缺少邀请只问一次附件或路径。以下命令供 Agent 执行，不要求成员自己准备 JSON、创建文件、配置 SSH/CA 或提供口令。

### 成员接入入口

本节集中维护邀请输入方式；Skill 不另存一套命令配方。先核对当前 `node tools/xj-dev/xj-dev.mjs --help` 与实现。Agent 接到完整邀请附件后，可以通过受控的非终端 stdin 传入完整 JSON：

```sh
node tools/xj-dev/xj-dev.mjs join --invitation-stdin --json
```

由 Agent 的进程调用 API 将附件字节写入子进程 stdin，最多 256 KiB；不把正文拼进 shell 命令、argv 或日志，不让成员在终端粘贴。此入口复用现有登记协议，不代表云端已部署本轮其他新接口。已有受限文件继续兼容：

```sh
node tools/xj-dev/xj-dev.mjs join --invitation-file /path/to/private-invitation.json --json
```

已有受限文件直接传路径，两种输入互斥；邀请附件由 Agent 接收和处理，不要求成员手建文件。旧 checkout 若只支持文件入口，由 Agent 将附件放入仓库外受限文件，Unix owner/0600、Windows 当前用户 NTFS DACL 保护，再调用兼容入口。邀请正文不进入聊天回显或 Git。具体输入校验与恢复方式见[工具说明](../tools/xj-dev/README.md#一次性邀请与设备登记)。本地命令落地与云端实测分别报告。

`join` 默认建立 local；需要共享环境时指定 `--mode cloud-api|cloud`。首次要在当前工作树导入团队固定基线时加 `--no-start`，先登记、准备依赖并 `baseline use ... --team --version VERSION --here`，再启动，避免先播种内置数据。工具生成独立设备 key、证明持有、取得受信 CA/pin 和配置；云端本人应用账号只写 `enrollment.accountFile`，本地测试账号只读当前环境返回的 `accounts.credentials.file`。成功后日常 `up`/`use` 复用登记配置，权限变化用 `refresh`。`--no-start` 只登记，不计完整环境启动。中断保留相同 home、邀请和 key 重试；丢失 key 才需新设备邀请。

当前工作树尚未绑定但同一 home 已登记时，先读取现有安全注册结果，再用 `refresh --device-file FILE` 绑定并更新该工作树的配置，不要求再次找邀请。只有获授 `page` 才检查云端页面；file-only 身份不创建 SSH 或应用账号。既有获准 connection-v1 仍可复用，不要求重新拼装主机、端口、pin 或 CA。

### 维护者入口

维护者使用 `xj-dev access invite --admin-config FILE --input-file FILE --out-file FILE`，通过既有 owner SSH 管理独立服务。邀请 out-file 含秘密，Unix owner/0600、Windows 当前用户 NTFS DACL 保护；交接渠道由维护者选择。`inspect`、`revoke-invitation`、`revoke-device`、`revoke-member` 和 `snapshot` 复用该入口，管理 socket 不在公网开放。

普通成员只领取给本人的受限邀请和应用身份。owner SSH、备份管理员、云厂商凭据及备份恢复材料留在维护流程，不能作为成员上手材料分发，也不能以现有备份能读为理由给普通成员使用。

已绑定邀请只恢复同一把 key，服务端不再把它作为可交给另一设备的未用邀请。设备撤销关闭该设备已有 SSH 并阻止新连接，保留其他设备；成员撤销还动态禁用应用身份及已有 session，作品保留。普通设备只有批准端口转发，无 owner shell、管理 socket 或任意系统配置权限，node 能力另授。

独立文件能力 `file:read`/`file:publish` 用于同服务的包目录与短期 OSS 授权；page/node 不自动授予文件权限，file-only 登记不创建 SSH 或应用账号。团队交接使用稳定编号，操作见 [团队复现编号与直传](../tools/xj-dev/README.md#团队复现编号与直传)。已签 URL 最长300秒，撤销停止新授权并报告已发 URL 剩余有效期。

部署目录、固定 helper、设备 proof、包目录、systemd 生命周期和备份恢复见[接入服务说明](../tools/xj-dev-access/README.md)。标准产品不含开发服务；只显式配置通用本机 account-control 时接收受控账号事务。真实验收与工程测试分别报告，不能把本地受控系统边界测试当成云端加入成功。

## 首次使用的目标流程

维护者生成限时的一次性邀请。成员首次调用 `$xunjie-development` 后，Agent 先复用已有材料，缺失时只需成员拖邀请附件或给路径；随后自动登记、准备本地及获准云连接，主动解释可用功能、适用场景、数据归属与实际缺口。首次之后直接执行正常任务，不重复介绍；跨会话记录的[当前边界与最小实现建议](development-tooling.md#首引导状态)另列。邀请本身授予该成员的有限权限，不要求先建立另一套账号密码或 OAuth 登录。

| 阶段 | 由谁处理 | 结果 |
| --- | --- | --- |
| 邀请 | 维护者通过 Agent 指定成员记录、角色及必要的应用测试身份 | 生成有期限、只允许登记一台设备的一次性邀请；通过明确指定的渠道交给本人，不发送共享管理员钥匙 |
| 本机准备 | 成员 Agent 检查仓库、固定版本 Node、Git、OpenSSH 等依赖 | 已满足、自动准备完成或需操作系统确认的项目分别报告；可中断后续做 |
| 设备登记 | 工具在本机生成设备专用密钥，用邀请提交公钥并证明持有对应私钥 | 成员与设备分别拥有 ID；邀请绑定该设备后不能登记另一把密钥；私钥留在本机 |
| 配置下发 | 开发接入服务返回获准目标、主机身份、能力范围、基线目录和连接配置 | 不要求成员填写主机地址、账号、端口和 `known_hosts` |
| 信任与连接检查 | 工具准备开发 HTTPS 证书信任，检查 SSH、应用健康和文件访问 | 系统确实要求交互时再提示成员完成；不通过跳过验证伪装为连接成功 |
| 本地环境建立 | 已有数据复用；首次按已核实的固定团队起点 `--here` 导入后启动，或使用明确说明的内置起点 | 返回页面、模式及数据归属；不假定团队基线已发布，不覆盖已有数据；首次无需安装不相关的 VM 或配置模型 Key |
| 首次介绍 | Agent 用本次真实结果解释本地开发、云端 API/页面、固定基线、复现交接及自然语言用法 | 明确哪些写本地、哪些写共享数据，执行/模型等能力是否真的就绪；后续只补待完成项 |

邀请持有人可领取其范围内的权限，因此邀请属于秘密接入材料：服务端保存摘要及到期/使用状态，CLI 从受限文件或秘密输入读取，不放入命令参数、日志或复现包。维护者可撤销未使用邀请。网络中断后，同一设备凭持有证明继续未完成步骤，不新增重复账号或把邀请重新开放给其他设备。

维护者发出的邀请已经表达接入授权，成员领取时不重复审批。系统证书信任等操作只在操作系统要求时由本人确认；地址、端口、身份、主机 pin 和连接文件由工具处理。登记后的日常连接使用本机设备身份，不反复领取邀请。工具不能要求成员复制公钥到服务器、手编 SSH 配置或每次手开隧道。

浏览器访问本机入口前，按[开发 CA 信任与精确撤销](../tools/xj-dev/README.md#开发-ca-的系统信任与精确撤销)完成正常系统信任。macOS 使用用户 login keychain；Windows 的 CurrentUser Root 在实际主机不支持 Add，改用具有写权限的 .NET LocalMachine Root，完成必要权限确认并按指纹读回。临时跳过证书告警或禁用 TLS 校验不计通过；结束验收只移除本次新增的确切CA；macOS按SHA256精确删除时使用`-t`同时移除该证书的当前用户trust，不清理原先已有或其他域的信任。

初次接入之外，正常使用只需“启动开发”“切到云端后端”“回本地”。重装系统或换新电脑时领取新设备邀请；旧设备可单独撤销。维护者的现有管理通道用于首次部署和故障恢复，不变成成员正常加入时必须手动配公钥的步骤。若以后需要企业身份校验或跨组织成员自动同步，再引入现成身份提供方；当前不把 GitHub OAuth 作为前置。

## 为什么还需要一小块开发接入服务

CLI 与文件存储能简化已经加入团队的成员操作，但不能自行批准一把尚未登记的公钥。为了保留“领取邀请后自动加入”的便利，保留一个轻量接入服务，职责限于邀请兑换、设备登记/撤销、配置下发、包目录和短期对象访问授权。

实现使用一个轻量进程及独立的小型 SQLite 存储，不按身份、配置和文件目录拆多个服务。维护者复用已有管理通道调用同一套工具管理邀请与设备；成员使用有限的接入接口，登记后凭与设备绑定的身份取得获准配置和包授权。文件内容直接传到私有对象存储；接入服务不代理大文件、运行成员代码或承载开发分支，也不进入学生产品的数据库和依赖。

首次部署由维护者准备可验证 HTTPS、独立存储与固定系统执行器；新成员由受限邀请文件取得入口和信任材料。已有预发私有 connection-v1 配置仍兼容，新成员使用 join 生成配置。对象存储授权由 #131 扩展，具体地址与凭据继续在仓库外分发。

接入服务不能接受任意 shell 命令。需要调整 SSH 成员配置时，交给只支持预定义成员操作的系统执行器；身份、角色、端口和目录由服务规则生成并验证。普通成员获得的凭据不能用于云主机 shell、sudo、云厂商控制台或修改其他成员权限。

## 便利与冗余的取舍

以减少实际操作和错误、实现与维护成本为依据，不以人数少或代码少直接决定删功能。

| 首版保留 | 为什么值得 |
| --- | --- |
| 一次性邀请、自动登记公钥与生成配置 | 新成员无需学习 SSH 配置，维护者无需逐台手填；小型接入服务直接支撑这一条完整流程 |
| 统一启动/切换、连接监督与自动重连 | 把每天重复的环境操作交给工具，同时保留明确的数据归属与失败状态 |
| 版本化基线、复现包与对象存储直传 | 解决实际的数据差异和 3 Mbps 出口限制，包在本地完整形成后也能独立交接 |
| 清晰帮助、一个项目 Skill 和统一工具说明 | 新 Agent 可自行核实使用方式，维护一份事实来源 |

首版不额外建设独立账号密码体系、OAuth、管理网页、通用 RBAC 框架、多服务编排或并行的 MCP 接口。它们有具体使用需求时可以增加，但不为未来假设提前承担。也不把成员手工拷贝密钥、反复编辑配置或重复领取下载链接包装成“轻量方案”。

## 权限模型

初期使用两种团队角色，并将执行节点接入作为额外能力，避免让每个人理解一套复杂权限系统。

| 能力 | 开发成员 | 维护者 |
| --- | --- | --- |
| 本地开发、读取获准基线 | 可以 | 可以 |
| 进入云端共享应用 | 使用个人获配的测试账号；受应用角色约束 | 同样遵守应用权限 |
| 读取团队复现包、发布自己的包 | 可以；不能覆盖他人的包 | 可以管理目录与配额 |
| 将场景提升为团队基线 | 提交候选场景 | 明确发布新版本 |
| 邀请成员、分配能力、撤销设备或成员 | 管理自己设备的受限操作 | 管理团队 |
| 发布部署、修改服务器运行策略 | 不随普通开发权限授予 | 通过单独维护入口执行 |
| 连接执行节点 | 按需申请并登记自己的节点 | 登记、停用和核对绑定 |

每人拥有独立开发身份，每台设备拥有独立密钥；浏览器隧道、文件访问和节点回连的授权分别表达。网络接入权限与应用中的教师/学生权限分开，不能因为是开发者就自动获得所有应用角色，也不能长期共享同一套应用测试密码。

默认产品仍在启动时读取 `allowedLoginUserIds`。可选本机 account-control 将原显式静态名单与当前 active managed identities 合并，对新 login 和已有 session 每次检查；其 ensure/disable 调用产品原账号事务。开发身份、应用教师/学生角色独立，动态授权不要求重启业务。完整加入验收仍需实际业务登录。

成员撤销包括停止新授权、撤销该成员设备密钥与会话、关闭其现有隧道，并禁用相关共享测试账号；单独撤销一台设备不影响其他设备。执行节点停用后停止新任务派发，既有任务沿原节点的取消/回收流程处理并报告。撤销成员不自动删除其作品或团队仍引用的包。

对象存储访问使用短期授权，建议单次访问凭证有效期从 5 分钟起，并支持续传时重新取授权。撤销成员立即停止签发新授权，已签发链接仍可能在到期前有效；这与关闭现有 SSH 会话不同。交接使用稳定包编号，不把短期下载链接当包的永久地址。

## 日常连接与故障处理

`up` 和 `use` 自动检查当前成员能力、连接状态和服务版本，只建立所需连接。成员不必保留一个手动启动 SSH 的终端。监督进程随开发会话管理连接，可复用自己创建的健康连接；不接管其他程序占用的端口。

| 情况 | 工具行为 |
| --- | --- |
| 网络切换、休眠唤醒或 SSH 意外断开 | 以有限退避恢复，例如 2、4、8 秒逐步到 30 秒；恢复后再校验服务，避免循环创建重复隧道 |
| 权限或设备被撤销 | 停止重试，明确报告失效范围；保留本地工作数据 |
| 主机身份与已验证配置不符 | 停止连接，要求通过可信维护入口更新配置；不自动接受陌生主机 |
| 凭证需重新确认 | 只重新完成必要的身份步骤，不重复安装、导入基线或重建环境 |
| 云端应用正常、执行节点离线 | 页面与普通数据操作保持可用，运行能力明确不可用，不改派到另一节点 |
| 服务未就绪或接口不兼容 | 保留当前可用环境，返回失败阶段及修复路径，不把 SSH 连通当业务成功 |
| 云端不可达 | 已准备的本地全栈继续可用；云端模式明确离线，不悄悄改为另一份数据 |

传输失败可从已校验分片恢复；业务写请求不能因重连而无限重发，已有幂等标识与请求结果核对需要保留。现有模式连接由受管监督进程串联 SSH 保活、有限退避和业务健康；终止性权限/主机身份失败停止重试。

## 针对这台服务器的资源策略

采用一套共享业务实例，个人开发分支运行在成员本地。服务器不为每位成员启动独立前后端，也不运行 C/HDL 编译虚拟机或本地模型。新增开发接入进程只处理少量元数据。

以下内存/CPU预算已依据 #133 的 e03 五成员完整窗口确定为模板值，实际主机已由负责人通过持久set-property应用，properties与内核cgroup值读回一致，所有PID/ExecStart不变；其余策略仍按各自验收边界判断，不据模板存在声称全部生效：

私有复现 bucket 的 ECS RAM role 只授予 `team/*` 对象的 `GetObject`、`PutObject`、`DeleteObject`、`ListParts`、`AbortMultipartUpload`。`ListMultipartUploads` 单独授予这个专用 bucket 的 bucket 资源；它不支持 `oss:Prefix` 条件，附加该条件会使请求返回 403。`oss:Prefix` 用于 ListObjects，不能照搬到 multipart 列举，详见[官方 RAM action 表](https://www.alibabacloud.com/help/en/ram/api-object-storage-service)。此角色不授予 `ListObjects`、`ListBuckets` 或存储管理权限。服务始终按目录记录的精确 owned key 列举、过滤和清理；成员设备只得到该 key/分片/Range 的短期签名 URL，不得到 role 或 STS 凭据。

发布采用 CI 构建后由云端拉取经过校验的运行产物：构建器在 GitHub Actions 上产出带逐文件摘要的产物并发布 Release，`deploy-artifact.py` 下载校验、装配、切换并在健康探测失败时回退到上一个版本及其备份。原生依赖与 Linux、CPU 架构和项目 Node 版本在构建与部署两端核对，不复制成员电脑的 `node_modules`。正式服务器已于 2026-10-23 从源码构建迁到旧产物协议，旧源码部署脚本与单元已删除。新增不可变产物 tag + bound Release 协议已通过 integration 候选 CI，正式 main 仍运行 `d07dc339` 的旧协议；在负责人决定合 main、首个 bound main Release 就绪前，保留兼容的正式发布器与 `artifactBranch` 配置，不将 strict candidate 部署器直接覆盖生产。切换顺序见[云基础设施模板](../tools/i0-cloud/README.md)。预算属性现位于unit模板的`[Service]`内；负责人仅通过持久set-property更新现行正式服务预算，不重启、不替换unit，原PID91972/argv保持。只有下次安装新shared模板才默认加入已在e03候选验证的ss16，不能声称正式旧d07已经使用该flag。

静态资源已在构建阶段预压缩（gzip 与 brotli 边车）：带内容摘要的资源一年不可变缓存，HTML 入口 no-cache 并以 ETag 协商，新版本与回退各用独立发布目录，不混用资源。静态服务对不超过 2 MiB 的文件一次写出，更大的文件流式转发，不在业务进程内整体读入大文件。业务数据与开发成员数据使用独立存储，备份也覆盖各自恢复所需内容。
