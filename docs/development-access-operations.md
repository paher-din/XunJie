# 开发成员接入、远程权限与云端运行

更新：2026-10-23。范围为 Robert 确认的 **2–5 人同时开发，Windows 与 macOS 均可接入**。这是工程设计，新的加入流程、成员管理服务和对象存储尚未实施，资源策略工具已交付但未在服务器应用。当前服务器的实测事实见[配置与运行核查](references/2026-10-23-development-server-assessment.md)。模式切换与基线操作见[开发工具设计](development-tooling.md)，已交付的产物发布与加密备份工具见[云基础设施模板](../tools/i0-cloud/README.md)。

## 首次使用的目标流程

维护者生成限时的一次性邀请，成员把邀请交给自己的开发 Agent 并说“帮我加入团队并启动开发环境”。Agent 调用 `join`，自动生成本机设备密钥、登记公钥、取得配置并验收连接。首版通过可信渠道交接邀请来授予该成员的有限权限，不要求先建立另一套账号密码或 OAuth 登录。

| 阶段 | 由谁处理 | 结果 |
| --- | --- | --- |
| 邀请 | 维护者通过 Agent 指定成员记录、角色及必要的应用测试身份 | 生成有期限、只允许登记一台设备的一次性邀请；通过明确指定的渠道交给本人，不发送共享管理员钥匙 |
| 本机准备 | 成员 Agent 检查仓库、固定版本 Node、Git、OpenSSH 等依赖 | 已满足、自动准备完成或需操作系统确认的项目分别报告；可中断后续做 |
| 设备登记 | 工具在本机生成设备专用密钥，用邀请提交公钥并证明持有对应私钥 | 成员与设备分别拥有 ID；邀请绑定该设备后不能登记另一把密钥；私钥留在本机 |
| 配置下发 | 开发接入服务返回获准目标、主机身份、能力范围、基线目录和连接配置 | 不要求成员填写主机地址、账号、端口和 `known_hosts` |
| 信任与连接检查 | 工具准备开发 HTTPS 证书信任，检查 SSH、应用健康和文件访问 | 系统确实要求交互时再提示成员完成；不通过跳过验证伪装为连接成功 |
| 本地环境建立 | 工具获取固定基线、生成本地测试身份、启动本地前后端 | 返回页面和当前模式；首次无需安装不相关的 VM 或配置模型 Key |

邀请持有人可领取其范围内的权限，因此邀请属于秘密接入材料：服务端保存摘要及到期/使用状态，CLI 从受限文件或秘密输入读取，不放入命令参数、日志或复现包。维护者可撤销未使用邀请。网络中断后，同一设备凭持有证明继续未完成步骤，不新增重复账号或把邀请重新开放给其他设备。

维护者发出的邀请已经表达接入授权，成员领取时不重复审批。系统证书信任等操作只在操作系统要求时由本人确认；地址、端口、身份、主机 pin 和连接文件由工具处理。登记后的日常连接使用本机设备身份，不反复领取邀请。工具不能要求成员复制公钥到服务器、手编 SSH 配置或每次手开隧道。

初次接入之外，正常使用只需“启动开发”“切到云端后端”“回本地”。重装系统或换新电脑时领取新设备邀请；旧设备可单独撤销。维护者的现有管理通道用于首次部署和故障恢复，不变成成员正常加入时必须手动配公钥的步骤。若以后需要企业身份校验或跨组织成员自动同步，再引入现成身份提供方；当前不把 GitHub OAuth 作为前置。

## 为什么还需要一小块开发接入服务

CLI 与文件存储能简化已经加入团队的成员操作，但不能自行批准一把尚未登记的公钥。为了保留“领取邀请后自动加入”的便利，保留一个轻量接入服务，职责限于邀请兑换、设备登记/撤销、配置下发、包目录和短期对象访问授权。

建议用一个轻量进程及独立的小型 SQLite 存储实现，不按身份、配置和文件目录拆多个服务。维护者复用已有管理通道调用同一套工具管理邀请与设备；成员使用有限的接入接口，登记后凭与设备绑定的身份取得获准配置和包授权。文件内容直接传到私有对象存储；接入服务不代理大文件、运行成员代码或承载开发分支，也不进入学生产品的数据库和依赖。

首次部署这部分由维护者完成：可验证的 HTTPS 入口、邀请/设备存储、受限系统配置操作，以及对象存储授权。当前成员配置主要是预发私有文件，公网入口查询仅见 SSH 放行；自助接入所需 HTTPS 入口不是当前已有能力。具体地址、主机信任材料与凭据继续在仓库外分发。

接入服务不能接受任意 shell 命令。需要调整 SSH 成员配置时，交给只支持预定义成员操作的系统执行器；身份、角色、端口和目录由服务规则生成并验证。普通成员获得的凭据不能用于云主机 shell、sudo、云厂商控制台或修改其他成员权限。

## 便利与冗余的取舍

以减少实际操作和错误、实现与维护成本为依据，不以人数少或代码少直接决定删功能。

| 首版保留 | 为什么值得 |
| --- | --- |
| 一次性邀请、自动登记公钥与生成配置 | 新成员无需学习 SSH 配置，维护者无需逐台手填；小型接入服务直接支撑这一条完整流程 |
| 统一启动/切换、连接监督与自动重连 | 把每天重复的环境操作交给工具，同时保留明确的数据归属与失败状态 |
| 版本化基线、复现包与对象存储直传 | 解决实际的数据差异和 3 Mbps 出口限制，包在本地完整形成后也能独立交接 |
| 清晰帮助、一个项目 Skill 和统一工具说明 | 新 Agent 可自行核实使用方式，维护一份事实来源 |

首版不额外建设独立账号密码体系、OAuth、管理网页、通用 RBAC 框架、多服务编排或并行的 MCP 接口。它们有具体使用需求时可以增加，但不为未来假设提前承担。也不把成员手工拷贝密钥、反复编辑配置或重复领取下载链接包装成“轻量方案”。

## 权限模型

初期使用两种团队角色，并将执行节点接入作为额外能力，避免让每个人理解一套复杂权限系统。

| 能力 | 开发成员 | 维护者 |
| --- | --- | --- |
| 本地开发、读取获准基线 | 可以 | 可以 |
| 进入云端共享应用 | 使用个人获配的测试账号；受应用角色约束 | 同样遵守应用权限 |
| 读取团队复现包、发布自己的包 | 可以；不能覆盖他人的包 | 可以管理目录与配额 |
| 将场景提升为团队基线 | 提交候选场景 | 明确发布新版本 |
| 邀请成员、分配能力、撤销设备或成员 | 管理自己设备的受限操作 | 管理团队 |
| 发布部署、修改服务器运行策略 | 不随普通开发权限授予 | 通过单独维护入口执行 |
| 连接执行节点 | 按需申请并登记自己的节点 | 登记、停用和核对绑定 |

每人拥有独立开发身份，每台设备拥有独立密钥；浏览器隧道、文件访问和节点回连的授权分别表达。网络接入权限与应用中的教师/学生权限分开，不能因为是开发者就自动获得所有应用角色，也不能长期共享同一套应用测试密码。

现有应用的 `allowedLoginUserIds` 在启动时读入，核查时仅配置两个账号。邀请流程要复用现有应用账号机制准备个人测试身份并更新授权，不能只打通 SSH 就报告全流程完成，也不能每次邀请成员就悄悄重启共享业务后端。需要时补充受控的授权更新接口，范围限于当前加入流程，不重建一套应用账号系统。

成员撤销包括停止新授权、撤销该成员设备密钥与会话、关闭其现有隧道，并禁用相关共享测试账号；单独撤销一台设备不影响其他设备。执行节点停用后停止新任务派发，既有任务沿原节点的取消/回收流程处理并报告。撤销成员不自动删除其作品或团队仍引用的包。

对象存储访问使用短期授权，建议单次访问凭证有效期从 5 分钟起，并支持续传时重新取授权。撤销成员立即停止签发新授权，已签发链接仍可能在到期前有效；这与关闭现有 SSH 会话不同。交接使用稳定包编号，不把短期下载链接当包的永久地址。

## 日常连接与故障处理

`up` 和 `use` 自动检查当前成员能力、连接状态和服务版本，只建立所需连接。成员不必保留一个手动启动 SSH 的终端。监督进程随开发会话管理连接，可复用自己创建的健康连接；不接管其他程序占用的端口。

| 情况 | 工具行为 |
| --- | --- |
| 网络切换、休眠唤醒或 SSH 意外断开 | 以有限退避恢复，例如 2、4、8 秒逐步到 30 秒；恢复后再校验服务，避免循环创建重复隧道 |
| 权限或设备被撤销 | 停止重试，明确报告失效范围；保留本地工作数据 |
| 主机身份与已验证配置不符 | 停止连接，要求通过可信维护入口更新配置；不自动接受陌生主机 |
| 凭证需重新确认 | 只重新完成必要的身份步骤，不重复安装、导入基线或重建环境 |
| 云端应用正常、执行节点离线 | 页面与普通数据操作保持可用，运行能力明确不可用，不改派到另一节点 |
| 服务未就绪或接口不兼容 | 保留当前可用环境，返回失败阶段及修复路径，不把 SSH 连通当业务成功 |
| 云端不可达 | 已准备的本地全栈继续可用；云端模式明确离线，不悄悄改为另一份数据 |

传输失败可从已校验分片恢复；业务写请求不能因重连而无限重发，已有幂等标识与请求结果核对需要保留。当前脚本已有 SSH 保活参数，但自动监督、恢复和业务健康串联仍待实现。

## 针对这台服务器的资源策略

采用一套共享业务实例，个人开发分支运行在成员本地。服务器不为每位成员启动独立前后端，也不运行 C/HDL 编译虚拟机或本地模型。新增开发接入进程只处理少量元数据。

以下数值是 **2–5 人场景的初始验收候选，不是已应用配置**：

| 资源 | 初始策略 | 验证与调整条件 |
| --- | --- | --- |
| 常驻内存 | 应用以 512 MiB 软阈值、768 MiB 最后上限作为候选；接入进程以 128/256 MiB 作为候选；常态保留至少 512 MiB 可用内存 | 用真实图片、模型上下文和五人操作测峰值后再应用；当前空闲用量不能证明这些上限足够 |
| CPU | 业务权重高于维护任务；后台维护串行；云端不再构建，产物由 CI 产生后拉取校验 | 维护单元模板已设低权重（`CPUWeight=20`、`Nice=10`），部署与备份单元共用同一把 flock 维护锁互斥；业务单元候选权重待实测峰值后启用 |
| 模型调用 | 单进程共享预算：全局 2、每成员 1；最多 20 等待、120 秒、等待 payload 合计 32 MiB；个人对话/学生帮助/教师设计共用 | [预算与错误语义](../apps/teaching/server/personal-agent/README.md)；以上为待 #133 五人 900 秒实测调整的候选值，取消须等实际上游收尾才返还名额，不将等待或外部模型延迟当作 ECS CPU 不足 |
| 场景导出/恢复 | 每个目标环境一项写操作；云端导出一次一项；压缩优先在成员本机完成 | 不对同一课程库并行启动多个可写后端或任意压缩任务 |
| 文件传输 | 大文件直达对象存储；每成员先按一项、团队最多两项重传敏感的大文件操作；按摘要缓存与去重 | 以成员实际网络测续传和首次基线耗时；控制对象存储用量，不让客户端持有无限写凭据 |
| ECS 磁盘 | 可用空间低于 10 GiB 预警，低于 5 GiB 拒绝下载装配新产物与大包落盘，优先保持既有业务 | 部署脚本已实现两级磁盘门槛与下载限长；整体磁盘、包配额与缓存大小分别计算，避免只看数据库文件大小 |
| 版本与缓存 | 保留当前版本、最近若干成功回退版本（`keepReleases`）及显式固定版本；失败装配临时目录自动清理，旧 Release 与备份按保留数裁剪 | 部署脚本已实现发布目录保留策略、`.pinned` 固定版本与 `--prune`；清理只作用于部署自有目录，不触及业务数据与已发布场景 |

发布采用 CI 构建后由云端拉取经过校验的运行产物：构建器在 GitHub Actions 上产出带逐文件摘要的产物并发布 Release，`deploy-artifact.py` 下载校验、装配、切换并在健康探测失败时回退到上一个版本及其备份。原生依赖与 Linux、CPU 架构和项目 Node 版本在构建与部署两端核对，不复制成员电脑的 `node_modules`。正式服务器已于 2026-10-23 从源码构建迁到旧产物协议，旧源码部署脚本与单元已删除。新增不可变产物 tag + bound Release 协议已通过 integration 候选 CI，正式 main 仍运行 `d07dc339` 的旧协议；在负责人决定合 main、首个 bound main Release 就绪前，保留兼容的正式发布器与 `artifactBranch` 配置，不将 strict candidate 部署器直接覆盖生产。切换顺序见[云基础设施模板](../tools/i0-cloud/README.md)。业务单元内存预算仍以候选注释保留，测出真实五人峰值后由 #133 验证启用，不把维护任务样本当作容量结论。

静态资源已在构建阶段预压缩（gzip 与 brotli 边车）：带内容摘要的资源一年不可变缓存，HTML 入口 no-cache 并以 ETag 协商，新版本与回退各用独立发布目录，不混用资源。静态服务对不超过 2 MiB 的文件一次写出，更大的文件流式转发，不在业务进程内整体读入大文件。业务数据与开发成员数据使用独立存储，备份也覆盖各自恢复所需内容。

## 监测、备份和扩容触发

现有阿里云 CMS 已接入 CPU、可用内存、磁盘、服务健康与发布结果监控：标准 C++ agent 已运行，独立 systemd 采样器每 5 分钟上报；健康与发布结果采用 0/1 指标，内存低于 384 MiB、磁盘低于 10/5 GiB 分别上报不健康标记。CMS 已配置自定义指标 `< 1` 连续两次、粒度 300 秒的规则，CPU 沿用既有 85% 连续三次、粒度 300 秒的规则；均复用既有联系组。部署脚本 `--status` 输出水位、当前与可回退版本、备份、上次发布结果及 `actions`。配置、凭据范围及维护步骤见[监控说明](../tools/i0-cloud/README.md#持续监控)，CMS 实际点与规则状态见[验收记录](references/2026-10-23-cloud-release-review-fixes.md)。只检查正常状态、配置和 dry-run，未主动发送测试通知。队列长度、请求延迟和五人负载行为留给 #133 整体验收，不据此声称容量已通过。

备份已由 `backup-retained.mjs` 实现并装入正式维护路径：课程库与个人模型存储经 SQLite Backup API 一致复制（含完整性与外键检查，排除源 WAL/SHM/journal），连同恢复材料用 AES-256-GCM 加密归档；日备保留 7、周备保留 4 的 timer 均 active，部署前课程库备份仍由部署器负责。包含密钥的恢复材料走维护者独享的加密备份路径，不能混入团队复现包。真实云端备份已复制到负责人 Mac，使用该设备 0600 密钥在新隔离目录恢复 10 文件、两库 integrity/外键通过，解密临时文件已清理。独立设备副本不等于离线介质；各库一致也不等于跨存储原子快照。接入服务尚未交付，其新增数据备份由 #133 纳入，本票不声称全链路灾备验收。

先按上述职责分配与候选参数验证，不因低配规格直接购买升级。若 2–5 人的目标工作流在构建和大文件移出后仍持续内存紧张，再评估 4 GiB 规格；若问题来自 3 Mbps 出口，则针对文件路径或带宽处理，不能靠增加 CPU 解决。对象存储有独立资源与费用，开通前需明确区域、容量/流量预算和生命周期；本轮没有创建或购买资源。

## 完成标准

1. 新 Windows、macOS 设备通过一次性邀请及必要系统确认完成加入，无需成员手改连接文件或要求维护者再手填公钥；中断重试不生成重复账号、设备或环境。邀请过期、重复领取、登记后撤销均有明确结果。
2. 五位成员同时执行登录、课程查看、编辑保存与提交反馈；同时包含模型队列和文件传输，记录内存、错误率及普通 API 延迟，验证资源竞争时的行为。负载时长、延迟与错误率的通过目标集中在[正式规范的 Testing Decisions](https://github.com/paher-din/XunJie/issues/126#testing-decisions)，不把本文件候选资源参数当作已经验证的容量。
3. 网络切换和休眠恢复后能自动重连；成员撤销关闭目标连接并阻止新授权，其他成员不受影响；大文件失败可续传。
4. 本地、云端后端、云端部署三种模式切换不混用数据与浏览器现场；基线更新保留旧副本；模式切换不会自动部署。
5. 低磁盘、服务重启、发布失败与备份恢复都有可验证结果；普通用户产品安装不携带或连接开发接入服务。
6. 每个替换阶段完成[旧入口清理](development-tooling.md#旧连接实现配置与说明的替换清理)，仓库中被替代的连接实现、配置与使用说明实际删除，保留能力的调用已迁移；不以新增一套可用工具代替清理交付。
