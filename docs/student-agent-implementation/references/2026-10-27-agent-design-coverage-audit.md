日期：2026-10-27。对应[总体架构与复用取舍：模块边界、Agent 内核和部署方式](https://github.com/paher-din/XunJie/issues/119)。依据：负责人要求长期最终设计，指出 Agent tool_use、Skills、MCP、plugin 与 system prompt 尚未充分讨论，并要求为课程可复用能力取独立名称。

本次审计与议题范围补充见[进展记录](https://github.com/paher-din/XunJie/issues/119#issuecomment-6437717432)，不是整体 resolution。

本审计保留补齐前的缺口与原因。当前逐项工程方案见[Agent 能力与质量契约](2026-10-27-agent-capabilities-design.md)，开发调试选型见[观测与评估研究](2026-10-27-agent-observability-evaluation-research.md)。命名与课程内个人扩展边界已确认；本轮进一步确认新消息模式、过程显示要求及无课程自主学习，形成[交互设计](2026-10-27-agent-interaction-design.md)、具体能力表与完整请求走查。总体设计已按[最终决议](https://github.com/paher-din/XunJie/issues/119#issuecomment-6443526782)收束，尚未实施或验收；下文“补齐前”的缺口保留作审计来源，不作为当前仍未回答的清单。

## 审计结论（补齐前）

**完整 Agent 设计尚未完成。** 目前已形成的是模型协议、课程能力宿主、教学事实、可靠保存/执行以及运行/部署的多项契约。它们提供了必要基础，但没有完整回答“本次 Agent 按什么指令、看哪些信息、能发现和调用什么能力、怎样处理过程中的新输入、如何判断交付合格”。此前把总体运行/部署设计称为完整最终设计过早，现已修正状态。

缺口多为设计尚未闭合，不能统一记作“以后实现”。同时，也不能把已经决定的权限、版本、原生续接和教学边界抹掉重做。以下核对当前设计文档、GitHub 议题及相关代码，排除 `docs/archive/`；没有执行模型调用或生产测试。

## 术语：课程组件与 Agent 工具分开

负责人已要求按新名称更正文档：原 **课程工具（Course Tool）** 统一称为 **课程组件（Course Component）**。它表达可装入课程的完整能力单元，覆盖有界面和无界面的能力；“组件”在这里是课程装配层的概念。已有决议中的 Course Tool 按此映射阅读，历史议题标题和用户原话保留。

| 名称 | 回答的问题 | 示例与关系 |
| --- | --- | --- |
| 课程组件（Course Component） | 学生工作区和课程获得什么可复用能力 | 波形查看器、虚拟实验板、交互练习；可以包含视图、状态、执行能力和资源 |
| 组件实例（Component Instance） | 某个活动实际使用哪一份组件及其状态 | 同一组件版本给不同学生建立独立实例，沿用已定版本和状态恢复契约 |
| Agent 工具（Agent Tool） | 模型可以请求哪一个具体操作 | 读取某个信号、运行仿真、修改获准对象；每项有可调用定义、参数、结果及实际能力绑定 |
| 执行命令（Command） | 某个操作实际被谁接受、依据什么执行、结果是什么 | 一次固定输入的仿真命令及其回执；模型 tool-call ID 与业务命令身份分别关联 |
| Skill | Agent 如何完成一类工作、使用哪些能力与资源 | 波形诊断步骤或课程允许的指导方法；说明不自动授予权限，也不等于执行接口 |
| MCP | 怎样接入外部服务器提供的能力 | tools、resources、prompts 分别确定项目接入范围；MCP Apps 另负责相应交互载体 |
| 扩展包（Plugin） | 怎样分发和装配一组扩展贡献 | 可讨论打包组件、Agent tools、Skills 或 MCP 配置的方式；具体允许贡献什么尚须决定，包不自带使用授权 |

一个课程组件可以提供零个或多个 Agent tools；Agent tools 也可以来自平台能力或外部服务，不必附带课程界面。Skill 可以指导使用若干 Agent tools，MCP 可以提供外部操作和资料，Plugin 是装配与分发层。这几项不应作为同一级“工具”混用。

教师侧统一使用“组件目录 / 教师组件库（Component Catalog / Teacher Component Library）”。每次运行可见的模型工具集合另称 `AgentToolRegistry`，两者不能共享一个含义含混的 catalog。本次同步当前设计文档与旧资料的映射说明，不修改生产代码标识。

## 审计发现的 Agent 设计缺口

| 主题 | 现有覆盖 | 仍需形成的具体答案 |
| --- | --- | --- |
| Agent 定义与运行模式 | 学生面对连续 Agent，后台生成/画像可作为任务，教学职责已有边界 | 一份 Agent 配置由哪些角色、提示、能力、上下文策略和输出契约组成；课程辅导、自由使用、内容生成与后台整理怎样切换或分工，哪些共享状态，哪些需要隔离 |
| Agent tool 发现与选择 | 运行前确定可用能力；课程组件有命令声明 | 运行可见工具从哪里来，怎样按活动/主体/课程/能力筛选，命名冲突和数量过多怎样处理；变化时如何保持工具版本与原生历史兼容；哪些动作由模型选择，哪些由确定性规则发起 |
| Agent tool 调用与结果 | 参数校验、固定输入、效果与回执原则已有 | schema 的项目表达及三协议映射；工具定义如何绑定真实命令/资源与权限；业务失败、调用失败、长任务、图片/结构化数据、资源引用、大结果裁剪和保留原件的语义 |
| Skills | 允许携带操作/教学说明与资源引用，不扩大权限 | 格式、来源、发现与触发、按需加载、资源依赖、冲突优先级、版本固定，以及恢复时怎样重现实际加载内容；开发者用的仓库 Skill 不等于学生 Agent 的 Skill runtime |
| MCP | tools/resources 接入方向与 Apps 宿主边界已有研究 | 连接与凭据归属、能力协商、注册/失效、授权后的命名与版本快照、取消/断线/未知结果；resources 如何检索和进入上下文；prompts 是否支持、由谁触发、与 Skill/平台指令是什么关系 |
| Plugin | 课程组件可提供视图、命令和观察等，早期底稿曾称 CapabilityPlugin | 扩展包能贡献哪些东西，谁能安装/发布，依赖如何装配、停用/升级影响什么；是否提供生命周期 hook 需要实际用例，不能默认导入任意执行代码的通用插件内核 |
| System prompt | 原生续接已约束 system/tools 前缀变化，旧代码有硬编码提示和局部版本字段 | 平台角色、教学原则、课程策略、当前任务及学生偏好如何组成；材料、工具结果与可执行指令的信任边界；冲突裁决、模板版本、实际装配记录及测试样本 |
| 上下文、检索与压缩 | 读取相关事实、记录来源、按新原生段处理压缩与换路线已有原则 | 每步取什么、按什么排序、哪些必须保留、如何分配窗口及输出预算；资料检索、引用与时效；压缩触发、摘要必须保留的未结问题、质量检查和失败路径 |
| Memory | 事实/判断/偏好分层、同课积累、跨课只共享通用偏好、学生纠错已经决定 | 何时形成候选记忆或判断、如何复核/更新/失效、怎样检索到当前上下文；来源冲突与证据不足时如何保留未知，不能把聊天摘要直接当长期事实 |
| 运行中新输入 | 固定输入、学生提问优先、冲突更新串行、独立请求与等待恢复已有边界 | 补充、纠正、转向和停止分别如何关联旧 Run；排队、步骤边界纳入、取消及多个回复呈现规则；不能由“创建新 Run”替代交互设计 |
| 输出质量与评估 | 教学候选先核对再展示，工程/浏览器/教学效果分开，主动引导已有评价维度 | 回答、主动提示和生成内容各自必须满足什么结构与依据，失败时怎样修订或结束；关联 prompt/工具/Skill/上下文版本与实际交付的追踪，跨课程正确性、帮助程度和工具使用回归样本 |

这些问题不自动要求向量数据库、多个 Agent 团队、通用 hook 引擎或任意 MCP 功能。最终设计需要明确采用的能力与范围，并能解释它如何服务学生场景；没有真实需要的扩展可以明确排除。

## 为什么遗漏

能从记录核实的是：原始需求包含这些内容，模型协议与课程宿主分别完成了局部决定，总体比较随后集中在持久运行和部署。Agent 能力如何装配、提示词怎样构造以及实际行为如何验收，没有形成同等完整的契约。

本轮设计工作的具体失误有三点：

- **术语混用遮蔽了范围。** 课程组件、模型 tools、命令与插件都用“工具/能力”概括，容易把完成宿主接入误认为完成 tool_use。
- **将原则当成完整设计。** “Skills 提供指导”“MCP 负责外接”“上下文取相关事实”确定了责任，却没有回答注册、选择、装配、失败与更新的行为。
- **收束顺序和覆盖检查不足。** 在 Agent 配置与能力契约尚未闭合时，先用内核探针和部署方案支撑整体定稿；缺少从原始要求到具体契约、使用场景和验证证据的逐项检查。

这是本轮设计完整性的问题。最终设计仍以长期使用为目标；不能通过把遗漏改称未来扩展来绕开。已有可靠运行证据继续保留，完整能力设计若暴露新的组合约束，就据此重新核对 RunDriver 等工程选择。

## 按审计补齐的收束路径

在当前总体架构议题内，按依赖关系补齐三个连贯部分，不为每个名词再建立一个框架：

1. **能力模型与装配：** 统一课程组件、AgentTool、Command、Skill、MCP 与 Plugin 的关系；形成可见工具注册、调用/结果及扩展包贡献契约，并用一个具体组件映射到多个 Agent tools 作例子。
2. **Agent 配置与上下文：** 形成角色/模式、system prompt 分层、Skill 装载、上下文与 Memory、压缩及版本记录规则；给出真实场景下完整的一次模型请求装配，而不是只给提示词标题。
3. **回合行为与质量：** 明确新输入、停止、等待、并发、输出核对与交付规则；给出可复现追踪与质量评价方式，检查对既有运行/部署契约的影响。

至少用以下完整场景走查这些部分：学生选中波形发问；生成交互卡片并经历工具失败/修订/长等待；运行过程中学生补充或改变要求；跨模型或能力配置变化后继续；外部能力断线或返回大结果。每个场景都要说明实际指令、上下文、可见工具、调用结果、状态变化与最终交付。无编译器课程仍能使用公共能力，第二门正式验收课程继续按原决议选择。

审计完成时尚无上述完整契约；现已按三组路径补成[具体方案](2026-10-27-agent-capabilities-design.md)，并新增[平台选型](2026-10-27-agent-observability-evaluation-research.md)。方案形成不等于产品边界已确认，也不等于生产实现、模型测试或教学验收。
