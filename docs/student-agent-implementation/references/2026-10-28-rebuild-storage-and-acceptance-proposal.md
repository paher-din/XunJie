## 本轮已明确的边界

1. **旧版只有开发数据。** 新架构可以直接重建数据结构和接口；不承担旧 API 兼容、旧 Agent 会话接续、旧实验进程迁移、生产双写或无停机切换。旧数据原件保留，确有价值的材料、作品或故障案例按明确对象提取；不因表存在而整库转换。
2. **分清产品能力、开发资料与当前讨论阶段。** 教师端的课程设计与制作是产品能力，当前地图尚未展开其深入设计，不从产品范围中删除。数字逻辑与部件设计的 ALU，以及下文 STAT 20 / Flights，是开发、验收与演示所需资料；其材料整理、任务说明、数据、起始作品、组件配置和验收案例属于开发交付工作，但这两套课程内容本身不是产品功能。选取样本不自动纳入正式开课或整学期课程建设；当前仍保留课程装配、预览、发布和反馈等必要教师接口。
3. **第二个样本有真实大学课程来源。** 负责人选择加州大学伯克利分校 STAT 20《Introduction to Probability and Statistics》的 2025 秋季 Flights 实验，替代此前没有课程出处的泛称“统计／数据分析任务”。
4. **长期架构要求不缩减。** [总体架构决议](https://github.com/paher-din/XunJie/issues/119#issuecomment-6443526782)中的六单元组合、个人/学校空间、持久 RunDriver、三协议原生记录、单一写入责任、未知效果查询及恢复要求继续成立。首次重建不需要旧版兼容，不等于未来已发布数据可以随升级丢失。

### 两个样本应覆盖的差异

以下是产品验证用途，不是改写原课程，也不宣称已完成验证。

| 维度 | ALU 样本 | Flights 样本提供的补充 |
| --- | --- | --- |
| 作品与资料 | SystemVerilog、用例、位信号和波形 | 数据表、分析代码、图表、文字解释与可复现报告 |
| 有效反馈 | 位宽、运算选择和实际输入输出行为 | 数据处理与图表是否对应、统计量是否适用、解释是否由证据支持 |
| 判断与未知 | 公共行为约定可做穷举检查；成功不直接证明掌握 | 可核对计算结果，但对图形结构和统计解释的反馈不能退化为输出匹配 |
| 上下文引用 | 代码片段、输入、波形 | 表格行列、图表区域/数据子集、报告片段及其固定数据依据 |
| 状态恢复 | 作品、用例、已保存结果与当前运行的区分 | 分析输入/步骤、图表与报告的版本关联，未运行的新分析不能冒用旧图 |
| 装配与执行 | 浏览器 Icarus/WASM 适配 | R 与数据/绘图/报告依赖；据实际能力选择可复用环境或必要适配，不预设与 ALU 同一个执行器 |

Flights 本身仍包含编程和有确定结果的计算题。其价值在于多种作品、数据依赖和解释性反馈，不以“统计课”这个名字就认定所有跨课程边界已覆盖。它也不能单独验证所有无计算活动、长期有状态实验或未来硬件课程；这些公共契约另用有明确目的的工程案例覆盖。

## 存储设计

**已确认：业务与持久运行所需的权威事务记录统一使用原生 PostgreSQL；本机实例由产品管理，学校部署可使用受支持的既有实例。** 资源默认由所属服务保存为文件，需要时接 S3 兼容后端。该架构选择不代表已完成打包或证明总成本最优。事实与其他路线的取舍见[存储研究](2026-10-28-storage-options-research.md)。

### 从实际约束推导

1. **学生需要可直接使用的产品。** 已定要求是不用手配数据库、端口或容器，并没有“后台必须零进程”或“安装包必须极小”的约束。本机组合原本就需要可信服务来保存和推进 Run；易用性应由安装与运行管理实现，不能直接推出本机必须 SQLite。
2. **同一产品要覆盖本机、学校和混合部署。** 活动、作品、预算、领取代际、去重与恢复不应因部署改变含义。统一引擎可以共用 SQL、事务实现、schema 与迁移体系，避免每次业务变化都处理两种数据库语义；各部署仍需验证网络、配置和故障行为。
3. **学校部署要容纳共享事务和不同对象并发推进。** PostgreSQL 提供并发事务与既有备份/维护工具，适合承担这一角色。SQLite 通过领域 API 也能服务学校，只是每库写事务串行；尚无实际负载证据证明它不够用，因此保留为统一引擎的有效备选，而不是先假定必须引入第二后端。
4. **权衡的是持续成本放在哪里。** 统一 PostgreSQL 把成本集中在受支持平台的安装、进程、版本和恢复管理；双引擎把成本带入日常 schema、查询、事务、迁移和回归验证。当前产品已经承担本机服务管理，且没有更强的轻量约束，优先选择前者。安装与维护不是一次性工作，不能声称包装一个库就已消除成本。

依据：[SQLite 的服务端使用与选型边界](https://sqlite.org/whentouse.html)、[PostgreSQL 并发控制](https://www.postgresql.org/docs/18/mvcc-intro.html)、[原生服务控制](https://www.postgresql.org/docs/18/app-pg-ctl.html)。

| 所在边界 | 建议的存储 | 负责的事实 |
| --- | --- | --- |
| 浏览器客户端 | IndexedDB | 当前草稿、组件实例的本机状态、固定引用与待发内容；已落本机不等于服务已接收 |
| 在个人设备运行的权威服务 | 产品管理的原生 PostgreSQL | 该服务负责的事务记录；可属于个人空间，也可服务于学校空间的本机绑定 |
| 学校或其他共享服务 | 同一受支持 PostgreSQL 引擎与 schema | 该服务负责的课程/成员、学习数据、运行/预算等事务记录，按照既定模块分配写入责任 |
| 资源与大记录 | 所属服务管理的文件目录，或明确配置的 S3 兼容后端 | 课程资料、数据集、图片、波形、报告、原生模型大记录；访问和保留责任随所属对象分别管理 |

数据库是服务依赖，不按个人/学校空间另造一套数据架构。一个本机安装组合通常共用一个 PostgreSQL 实例，各模块保持表/schema 与写入责任边界；六单元不等于六个数据库进程。只使用学校网页的学生无需安装数据库；仅当部署组合在本机承载相应权威服务时，产品才准备所需实例。跨机通过领域 API 访问所有者，不能因同用 PostgreSQL 就跨服务直写表或引入跨服务数据库事务。

浏览器待同步草稿、执行器内部工作目录和不可变资源有不同用途，继续使用各自合适的存储，不要求全部塞进 PostgreSQL；它们不另实现一套同义的课程、活动或 RunStore。执行器自身持久回执的实现仍须兑现命令查询与去重契约，不能把临时工作文件当成完成回执。

### 四条路线的取舍

| 路线 | 能解决什么 | 长期代价与本轮判断 |
| --- | --- | --- |
| 统一 SQLite | 单一数据实现、无需数据库服务；通过领域 API 支持本机及共享单宿主 | 每库一个 writer，安装最轻；真实负载可接受时是有效长期方案。当前没有容量实测，不能宣称不足或无限适用。 |
| 本机 SQLite / 共享 PostgreSQL | 两端分别使用擅长的部署形态 | 两套事务、类型映射、迁移和故障验证持续存在。没有必须同时选它们的已知约束，撤回默认推荐。 |
| 本机 PGlite / 共享 PostgreSQL | 接近 PostgreSQL 的 SQL，减少本机原生二进制准备 | PGlite 单用户/独占连接，连接复用不等于原生多会话并发；扩展、文件持久化和恢复工具也有边界。仍是两个运行后端，不能借“同源”消除验证成本，不作为本轮默认。 |
| 统一原生 PostgreSQL | 共用事务、SQL、schema、迁移与主要故障案例；支持多个服务连接 | **负责人已确认采用。** 产品承担本机运行管理、包体与资源占用、升级和跨平台安装验收；先做有界安装与恢复探针。 |

PGlite 的单连接与 socket 复用边界依据：[PGlite 文档](https://pglite.dev/docs/)、[PGlite Socket](https://pglite.dev/docs/pglite-socket)。[本机运行研究](2026-10-28-postgres-local-runtime-research.md)进一步核对了真实多会话、扩展、文件系统、取消协议和升级差异，并调查原生二进制路径。选择某个封装库与选择 PostgreSQL 是两层决定；不会因发现可用 npm 包就承诺安装、签名或升级已经解决。

### 本机数据库由产品管理

1. 使用产品私有数据目录和明确引擎版本，由安装/更新流程准备目标 OS 与架构的二进制；不要求学生手工安装 PostgreSQL、Homebrew 或 Docker，也不接管机器已有的数据库。初始化固定 UTF-8、时区及所需排序/扩展条件，不继承机器默认设置后宣称语义相同。
2. 服务管理层负责初始化、连接凭据、仅本机需要的监听、端口选择、就绪检测、进程唯一性、退出与崩溃恢复。关闭页面不等于立即终止已接收的工作；停止策略须遵守既定 Run 恢复与预算契约。官方 `initdb` / `pg_ctl` 提供基础操作，产品仍须完成监督与诊断。[initdb](https://www.postgresql.org/docs/18/app-initdb.html)、[pg_ctl](https://www.postgresql.org/docs/18/app-pg-ctl.html)
3. 应用 schema 迁移与数据库引擎升级分开管理；锁定受支持版本和扩展集合。本机与共享部署跑同一迁移链，开发/CI 的集成环境也使用 PostgreSQL，不用 SQLite 替身证明事务正确。小版本更新与跨大版本迁移分别处理；升级前冻结必要写入与派发，验证备份和资源清单，再升级/还原并核对记录。[PostgreSQL 升级](https://www.postgresql.org/docs/18/upgrading.html)
4. 同一引擎仍须验证去重、CAS、唯一约束、跨行预算、取消竞争和旧 worker 失权。原生协议原件不能依赖 JSONB 重编码保持字节不变；模型、工具或资源上传不占着数据库事务等待。部署迁移使用固定身份和可验证资源清单，明确交接唯一写入/推进权，不做两个实例的通用双向同步。
5. 实施第一阶段在 Windows 11 x64 与 Apple Silicon Mac 验证普通用户安装、含中文/空格路径、已有 PostgreSQL 共存、启动停止/异常终止恢复、备份还原及版本升级；记录包体、启动耗时、空闲与真实任务资源占用。实际交付包还要通过目标平台签名/安装流程。缺少这些证据就不能宣称本机交付完成，也不能预先许诺性能数字。

已发现可具体处理的复用缺口：所查 `embedded-postgres` wrapper 在 Windows 使用强制终止，并跳过 Windows 运行测试；其 Zonky 精简二进制未包含 `pg_dump`、`pg_restore`、`pg_upgrade`。因此优先用官方 `initdb` / `pg_ctl` 等工具建立有界的产品运行管理层，选择包含所需备份/升级工具的完整资源或受控子集，不能原样依赖该 wrapper 的退出 hook。源码版本与证据见[本机运行研究](2026-10-28-postgres-local-runtime-research.md#wrapper-可复用但不能原样认定为产品监督器)。最终 binary 来源与版本由打包探针确定。

若探针发现本机负担违反真实目标，先明确是哪项用户要求无法满足，再重新比较统一 SQLite 或其他路线；不静默引入第二套数据库，也不以未来探针替代当前的架构判断。

### 资源关联与恢复

小型正文与结构化状态可随所属元数据事务保存；图片、数据集、波形、报告及大型原生记录通过稳定资源引用保存，不把所有对象统一降为文本文件或巨大 JSON。资源身份包含归属、内容摘要、长度、格式版本和可解析定位，不采用会过期的 URL 或本机绝对路径作为长期身份。

1. 先登记稳定上传身份并完成资源持久写入，再在短事务中发布业务引用、状态和必要待发项。上传未知按原身份核实；没有可重读的完整模型结果，不产生工具待发项。
2. 已写资源但元数据提交失败可重新关联；不能以重跑模型/工具补资源。创建引用与资源清理有持久保留协议，Run、活动、提交和恢复清单仍引用的资源不得删除。
3. 产品备份同时记录数据库快照与资源清单，并校验可以恢复全部引用。多个库或资源后端不因时间相近而成为原子快照。默认升级/整套导出允许明确维护窗口；若以后要求在线升级，再按实际需求扩展。
4. 服务进程崩溃后从已确认持久记录恢复；宿主或介质损毁按实际独立备份恢复，记录可恢复到的时间。备份周期与保留策略由部署维护者配置，能力说明不能承诺未实现的零丢失或零停机。

S3 后端是部署选项，不是本地安装的必需服务。选定实现须验证本项目用到的条件写、内容校验、超时和删除语义；S3 API 兼容不自动等于所有供应商行为相同。[S3 的单对象一致性](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel)也不提供数据库与资源的原子事务。

## 重构与开发基线

### 直接重建的范围

新领域模型包含空间与成员、课程/组件及内容版本、活动、作品与快照、固定引用、提交、学习证据与可纠正判断，以及 Run/step/attempt、InputEvent/Inbox、Wait、Command、预算、原生模型记录和能力/Prompt/Skill 装配版本。数据与调度的所有权遵循前序决议，不将全部内容塞进一份聊天记录。

旧开发环境和新环境使用不同的数据目录、浏览器存储命名空间与环境身份。保留旧原件的动作与采用新基线分别执行；不在开发启动时自动转换、清空或接管旧环境。重新生成测试数据不等于恢复旧现场，也不等于允许覆盖同事的数据。

未来新架构的兼容升级有显式 schema/内容/协议版本与升级步骤；不兼容变更须能读取旧记录或完成有验证的迁移。Run、未结 Command/Wait、未知用量和引用资源的保留关系不能被升级脚本清空。部署位置改变时交接唯一写入与推进权，不通过换服务 URL 制造两个写者。

### 现有开发工具的复用与缺口

| 能力 | 当前事实 | 重构时的安排 |
| --- | --- | --- |
| 独立工作环境 | 依工作树与 instance 区分数据、浏览器 profile、缓存和进程；同路径切分支不会自动换数据 | 沿用隔离入口，新增 schema 与基线不兼容时创建新副本；界面/诊断能确认当前环境与数据版本 |
| 业务复现包 | `xj-repro/1` 记录源码、显式差异、锁文件、限定业务 SQLite 和附件；schema 不匹配拒绝恢复 | 适配新对象与数据存储，不把旧格式强塞给新模型；读取旧业务包与创建新包分别表达 |
| 数据 seed | `local-baseline-1` 使用测试辅助数据 | 将通用故障 fixture 与两个可审查演示样本分开版本化；不把占位文本当作真实课程材料 |
| 条件记录 | 有精确 Node、工具版本和锁文件摘要 | 补实际 OS/架构、所用执行器/依赖版本、公开配置内容身份、schema/seed/课程版本、输入步骤与结果 |
| Agent 调试包 | 已有设计和 Skill 路由，纯 Agent 包采集与 Phoenix 导入尚未实现 | 在真实运行接入后落实选定案例、原生记录、评分/实验和附件交接；读取旧结果不执行模型或工具 |
