## Standards

1. **P2，文档规范。** 新暂停项直接显示 `wait-expired` 等工程码。DESIGN 要求工程信息进入按需技术详情，影响操作的恢复提示直接可见。
2. **P3，判断项：可能的 Duplicated Code。** FIFO、转引导和显式续接重复初始化 Run、预算与后继关联；建议集中维护初始状态和预算。这是非阻塞维护判断，非硬规范违例。

## Spec

1. **P2，学生提问超时遗漏输入暂停。** 直接暂停 Run 而未结清未消费输入，queue 仍为 pending、缺少暂停原因及日志。不符合“所有未消费 steering/queue 作为可见暂停项保留原因”。
2. **P2，停止清理使合法结果无法通过维护校验。** 用固定观察摘要比较可变 command head；清理追加 `stoppedExecution` 后误报 corrupt。不符合“维护参与、资源保留、迁移及日常重启覆盖新增事实”。
3. **P2，部分续接完成后剩余暂停项失去继续入口。** 最新 Run 正常结束便隐藏所有选择控制，未选择的 paused steering 无法稍后继续。不符合“终态后由学生明确选择输入建立关联后继 Run”。
4. **P2，收起后再次编辑覆盖保留草稿。** 以服务器原文重建草稿；消费后查看/复制入口也会消失。不符合“已消费时明确失败并保护待发送内容”。

这些是首次源码审查结论，不将静态核对称作运行验证。Standards 初次 2 项（最高 P2）；Spec 初次 4 项（最高 P2），两个轴分别保留。

## 修复与回归

- 暂停项显示可理解的原因，原码放入“技术详情”。`run-records.ts` 统一根接收、FIFO、转引导、显式续接的初始状态与接收时预算；各入口保留自己的授权和原子事件顺序。
- 学生 Wait 到期在原事务中暂停所有剩余输入。新增真实 Agent/PG 场景先复现 pending 错误，修复后通过。
- 上下文固定时把完整 Wait outcome 与摘要提交为不可变观察事件。维护校验该观察和步骤计划，不比较后续清理 head。真实聚合、观察结果、停止原执行和 `agent.validate()` 先复现 corrupt，修复后通过。
- 完整轮结束后仍显示剩余暂停项的选择入口。实际 Chrome 先选择 queue、完成后再选择原来未选的 steering，建立第三个关联 Run。
- 收起/重开沿用本机草稿及预期版本，已消费后仍能查看不同的保留稿；成功修订更新本机版本。实际 Chrome 验证收起重开、刷新、丢回包及后台采用后草稿/焦点保留。

审查问题的定向原生 2/2、Chrome 2/2 通过；此前 #200 原生文件 15/15、普通 Web 与完整 Windows 包各 5/5 通过。修复前的一次并行长任务回归在更早的等待阶段超时，未当作目标红测；单独重跑才确认维护 corrupt。最终工程与平台结论见 [交付记录](wp07-200-input-control.md)。
